Factory Method Pattern - (Income Tax Calculator)

Definition

Provides an interface for creating a single product object, but lets subclasses decide which concrete class to instantiate.

Description

Use Factory Method when you want to delegate the instantiation of one type of object to subclasses. It focuses on creating a single product at a time.

Real-Time Example: Income Tax Calculator


public interface IIncomeTaxCalculator {
    decimal Calculate(decimal amount);
}

public class IndiaIncomeTax : IIncomeTaxCalculator {
    public decimal Calculate(decimal amount) => amount * 0.30m;
}

public class USAIncomeTax : IIncomeTaxCalculator {
    public decimal Calculate(decimal amount) => amount * 0.25m;
}

public abstract class TaxFactory {
    public abstract IIncomeTaxCalculator CreateIncomeTax();
}

public class IndiaTaxFactory : TaxFactory {
    public override IIncomeTaxCalculator CreateIncomeTax() => new IndiaIncomeTax();
}

public class USATaxFactory : TaxFactory {
    public override IIncomeTaxCalculator CreateIncomeTax() => new USAIncomeTax();
}

// Client
TaxFactory factory = new IndiaTaxFactory();
var taxCalc = factory.CreateIncomeTax();
Console.WriteLine(taxCalc.Calculate(1000)); // Output: 300

Abstract Factory Pattern - (Income Tax + Social Security)

Definition

Provides an interface for creating families of related or dependent objects without specifying their concrete classes.

Description

Use Abstract Factory when you need a set of related objects that must work together consistently. It focuses on creating families of products.

Real-Time Example: Tax Calculators (Income Tax + Social Security)


public interface IIncomeTaxCalculator { decimal Calculate(decimal amount); }
public interface ISocialSecurityCalculator { decimal Calculate(decimal amount); }

public class IndiaIncomeTax : IIncomeTaxCalculator {
    public decimal Calculate(decimal amount) => amount * 0.30m;
}
public class IndiaSocialSecurity : ISocialSecurityCalculator {
    public decimal Calculate(decimal amount) => amount * 0.12m;
}

public class USAIncomeTax : IIncomeTaxCalculator {
    public decimal Calculate(decimal amount) => amount * 0.25m;
}
public class USASocialSecurity : ISocialSecurityCalculator {
    public decimal Calculate(decimal amount) => amount * 0.062m;
}

public interface ITaxFactory {
    IIncomeTaxCalculator CreateIncomeTax();
    ISocialSecurityCalculator CreateSocialSecurity();
}

public class IndiaTaxFactory : ITaxFactory {
    public IIncomeTaxCalculator CreateIncomeTax() => new IndiaIncomeTax();
    public ISocialSecurityCalculator CreateSocialSecurity() => new IndiaSocialSecurity();
}

public class USATaxFactory : ITaxFactory {
    public IIncomeTaxCalculator CreateIncomeTax() => new USAIncomeTax();
    public ISocialSecurityCalculator CreateSocialSecurity() => new USASocialSecurity();
}

// Client
ITaxFactory factory = new USATaxFactory();
var incomeTax = factory.CreateIncomeTax();
var socialSecurity = factory.CreateSocialSecurity();

Console.WriteLine(incomeTax.Calculate(1000));       // 250
Console.WriteLine(socialSecurity.Calculate(1000));  // 62

Builder Pattern - (Building an Order)

Definition

Separates the construction of a complex object from its representation, allowing the same construction process to create different representations.

Description

Use the Builder Pattern when you need to create complex objects step by step. It helps avoid telescoping constructors (constructors with too many parameters) and makes object creation more readable and flexible.

Real-Time Example: Building an Order


// Product
public class Burger
{
    public string Bun { get; set; }
    public string Patty { get; set; }
    public string Sauce { get; set; }

    public override string ToString() => $"{Bun} Burger with {Patty} and {Sauce}";
}

// Builder
public class BurgerBuilder
{
    private Burger _burger = new Burger();

    public BurgerBuilder WithBun(string bun)
    {
        _burger.Bun = bun;
        return this;
    }

    public BurgerBuilder WithPatty(string patty)
    {
        _burger.Patty = patty;
        return this;
    }

    public BurgerBuilder WithSauce(string sauce)
    {
        _burger.Sauce = sauce;
        return this;
    }

    public Burger Build() => _burger;
}

// Client
var burger = new BurgerBuilder()
    .WithBun("Sesame")
    .WithPatty("Chicken")
    .WithSauce("Mayo")
    .Build();

Console.WriteLine(burger);

Output

Sesame Burger with Chicken and Mayo

Interview Insight

  • Creating complex DTOs or domain objects with optional fields.
  • Constructing configuration objects step by step.
  • Test Data Builders in unit testing.

Singleton Pattern - (Logger Service)

Definition

Ensures a class has only one instance and provides a global point of access to it.

Description

Use the Singleton Pattern when exactly one object is needed to coordinate actions across the system. It restricts instantiation of a class to a single object and provides a way to access that instance globally.

Real-Time Example: Logger Service


public sealed class Logger
{
    private static readonly Logger _instance = new Logger();

    // Private constructor ensures no external instantiation
    private Logger() { }

    public static Logger Instance => _instance;

    public void Log(string message)
    {
        Console.WriteLine($"[LOG]: {message}");
    }
}

// Client
class Program
{
    static void Main()
    {
        Logger.Instance.Log("Application started");
        Logger.Instance.Log("Processing data...");
        Logger.Instance.Log("Application finished");
    }
}

Output

[LOG]: Application started
[LOG]: Processing data...
[LOG]: Application finished

Interview Insight

  • Commonly used for logging, configuration settings, caching, or thread pools.
  • Ensures only one instance exists, avoiding conflicts or inconsistent state.
  • In C#, thread-safe singletons are often implemented using static readonly fields.

Adapter Design Pattern Example (Payment Gateway)

Think of the Adapter Design Pattern like a physical travel adapter. If you travel with a US laptop to Europe, your plug won't fit into the wall outlet. The power is there, but the interfaces don't match. You use an adapter to translate your plug into the shape the wall expects.

In software, the Adapter pattern lets two incompatible interfaces work together. This is incredibly common when integrating third-party SDKs into an existing codebase.

Scenario: E-Commerce Payment Processing

Imagine your application processes payments using an internal interface (ILocalPayment). You want to integrate a third-party SDK (Stripe), but Stripe's SDK uses entirely different method names and data structures. Instead of rewriting your entire core application, you build an Adapter.

1. The Existing System (What your app expects)

This is the current target interface your application relies on.

// The 'Target' interface
public interface ILocalPayment
{
    // Expects payment details as a string and amount as a double
    void ProcessPayment(string accountDetails, double amount);
}

// Our existing internal payment processor
public class LocalPaymentProcessor : ILocalPayment
{
    public void ProcessPayment(string accountDetails, double amount)
    {
        Console.WriteLine($"Processing local payment of ${amount} to account {accountDetails}.");
    }
}

2. The Third-Party Service (The Incompatible Class)

This is the external Stripe SDK. It has the features you need, but its signatures are completely different.

// The 'Adaptee' class (Incompatible third-party SDK)
public class StripePaymentSdk
{
    // It uses different parameter types and a different method name
    public void MakeStripeTransaction(int customerId, double amountInUsd, string currencyToken)
    {
        Console.WriteLine($"Stripe successfully charged Customer #{customerId} {amountInUsd} {currencyToken}.");
    }
}

3. The Adapter (The Translator)

This class implements your existing ILocalPayment interface, wraps the StripePaymentSdk, and handles the data translation internally.

// The 'Adapter' class
public class StripeAdapter : ILocalPayment
{
    private readonly StripePaymentSdk _stripeSdk;

    public StripeAdapter(StripePaymentSdk stripeSdk)
    {
        _stripeSdk = stripeSdk;
    }

    public void ProcessPayment(string accountDetails, double amount)
    {
        // 1. Translate the incoming data to what Stripe expects
        // (Extracting the numeric ID from a string format like "Cust5542")
        int stripeCustomerId = int.Parse(accountDetails.Replace("Cust", ""));
        
        // 2. Route the request to the incompatible Stripe method
        _stripeSdk.MakeStripeTransaction(stripeCustomerId, amount, "USD");
    }
}

4. Client Code Execution

The client application seamlessly interacts with both systems using the exact same interface code.

class Program
{
    static void Main()
    {
        // 1. Using our old, standard local payment system
        ILocalPayment standardProcessor = new LocalPaymentProcessor();
        standardProcessor.ProcessPayment("Account-9928", 150.00);

        Console.WriteLine(new string('-', 40));

        // 2. Using Stripe via the Adapter
        // The core application code doesn't change; it still targets ILocalPayment!
        StripePaymentSdk stripeSdk = new StripePaymentSdk();
        ILocalPayment stripeAdapter = new StripeAdapter(stripeSdk);
        
        // The application passes standard local data, and the adapter handles the translation
        stripeAdapter.ProcessPayment("Cust5542", 299.99);
    }
}
Real .NET Ecosystem Example: ADO.NET uses this pattern heavily. Classes like SqlDataAdapter act as adapters between physical database structures (SQL Server tables) and abstract memory objects (DataSet / DataTable) that your C# application interacts with.
Decorator Design Pattern Example (Coffee Shop)

Think of the Decorator Design Pattern like ordering a coffee. You start with a basic coffee (the base component). If you want milk, you wrap it with milk. If you want caramel, you wrap that milk-coffee with caramel. Each ingredient "decorates" the beverage, adding behavior and cost dynamically at runtime without creating a massive inheritance tree.

1. The Core Interface & Base Component

First, we define what a ICoffee is, and create a concrete implementation for a simple black coffee.

// The 'Component' interface
public interface ICoffee
{
    string GetDescription();
    double GetCost();
}

// The 'ConcreteComponent' - the basic object we will decorate
public class BlackCoffee : ICoffee
{
    public string GetDescription() => "Simple Black Coffee";
    public double GetCost() => 2.00;
}

2. The Decorator Base Class

The decorator implements the same interface but also holds a reference to an ICoffee object. It delegates the work to that object while allowing subclasses to modify the result.

// The 'Decorator' abstract class
public abstract class CoffeeDecorator : ICoffee
{
    protected readonly ICoffee _coffee;

    protected CoffeeDecorator(ICoffee coffee)
    {
        _coffee = coffee;
    }

    public virtual string GetDescription() => _coffee.GetDescription();
    public virtual double GetCost() => _coffee.GetCost();
}

3. Concrete Decorators

Now, we create specific ingredients (Milk and Caramel) that add their own descriptions and costs to the underlying coffee.

// Concrete Decorator A
public class MilkDecorator : CoffeeDecorator
{
    public MilkDecorator(ICoffee coffee) : base(coffee) { }

    public override string GetDescription() => $"{base.GetDescription()}, with Milk";
    public override double GetCost() => base.GetCost() + 0.50;
}

// Concrete Decorator B
public class CaramelDecorator : CoffeeDecorator
{
    public CaramelDecorator(ICoffee coffee) : base(coffee) { }

    public override string GetDescription() => $"{base.GetDescription()}, with Caramel";
    public override double GetCost() => base.GetCost() + 0.75;
}

4. Putting It Together (The Runtime Wrapping)

The beauty of this pattern is that you can stack these decorators in any order or combination at runtime.

class Program
{
    static void Main()
    {
        // 1. Order a plain black coffee
        ICoffee myCoffee = new BlackCoffee();
        Console.WriteLine($"{myCoffee.GetDescription()} -> ${myCoffee.GetCost():F2}");
        // Output: Simple Black Coffee -> $2.00

        // 2. Wrap it with Milk
        myCoffee = new MilkDecorator(myCoffee);
        Console.WriteLine($"{myCoffee.GetDescription()} -> ${myCoffee.GetCost():F2}");
        // Output: Simple Black Coffee, with Milk -> $2.50

        // 3. Wrap it again with Caramel
        myCoffee = new CaramelDecorator(myCoffee);
        Console.WriteLine($"{myCoffee.GetDescription()} -> ${myCoffee.GetCost():F2}");
        // Output: Simple Black Coffee, with Milk, with Caramel -> $3.25
    }
}
Real .NET Ecosystem Example: You actually use this in C# all the time with file streams! BufferedStream and CryptoStream are decorators that wrap around a standard FileStream to add buffering or encryption capabilities dynamically.
Composite Pattern Example (Shipping & Packaging - Logistics Domain )

In supply chain and logistics systems, shipments are often nested. A large shipping container contains pallets, which contain boxes, which contain retail products. The Composite Pattern allows us to compute shipping metrics (like weight or price) uniformly for a single product or an entire multi-tiered freight shipment.

1. The Component Interface

This defines the unified operation (CalculateWeight()) that both standalone products and shipping containers must implement.

// The 'Component'
public interface IShippable
{
    string Name { get; }
    double CalculateWeight(); // Returns weight in kilograms
}

2. The Leaf Node (Individual Product)

This represents the actual items being purchased. They have a fixed weight and cannot contain other items.

// The 'Leaf'
public class Product : IShippable
{
    public string Name { get; }
    private double _weight;

    public Product(string name, double weight)
    {
        Name = name;
        _weight = weight;
    }

    public double CalculateWeight() => _weight;
}

3. The Composite Node (The Box / Container)

This represents a container. It has its own structural weight (the empty box itself) plus the weight of any products or smaller boxes packed inside it.

// The 'Composite'
public class ParcelBox : IShippable
{
    public string Name { get; }
    private double _boxEmptyWeight;
    private readonly List<IShippable> _contents = new List<IShippable>();

    public ParcelBox(string name, double boxEmptyWeight)
    {
        Name = name;
        _boxEmptyWeight = boxEmptyWeight;
    }

    public void Pack(IShippable item)
    {
        _contents.Add(item);
    }

    public void Unpack(IShippable item)
    {
        _contents.Remove(item);
    }

    // Recursively calculates total weight: Box Weight + Weight of everything inside
    public double CalculateWeight()
    {
        double totalWeight = _boxEmptyWeight;
        foreach (var item in _contents)
        {
            totalWeight += item.CalculateWeight();
        }
        return totalWeight;
    }
}

4. Client Code Execution

The logistics application can measure the weight of the entire delivery manifest automatically.

class Program
{
    static void Main()
    {
        // 1. Individual items (Leafs)
        IShippable laptop = new Product("Pro Laptop", 2.2);
        IShippable mouse = new Product("Wireless Mouse", 0.15);
        IShippable keyboard = new Product("Mechanical Keyboard", 0.9);
        IShippable coffeeMug = new Product("Ceramic Mug", 0.4);

        // 2. Pack tech accessories into a small inner box (Composite 1)
        ParcelBox accessoriesBox = new ParcelBox("Accessories Box", 0.2); // Box weighs 0.2kg empty
        accessoriesBox.Pack(mouse);
        accessoriesBox.Pack(keyboard);

        // 3. Pack the laptop, the accessories box, and a mug into the main shipping crate (Composite 2)
        ParcelBox masterCrate = new ParcelBox("Master Shipping Crate", 1.5); // Crate weighs 1.5kg empty
        masterCrate.Pack(laptop);
        masterCrate.Pack(accessoriesBox); // Nested composite!
        masterCrate.Pack(coffeeMug);

        // 4. Uniform processing
        Console.WriteLine($"--- Logistics Weight Manifest ---");
        Console.WriteLine($"{laptop.Name} individual weight: {laptop.CalculateWeight()} kg");
        Console.WriteLine($"{accessoriesBox.Name} total weight: {accessoriesBox.CalculateWeight()} kg");
        
        Console.WriteLine(new string('-', 40));
        
        // The manifest system handles the master container seamlessly
        Console.WriteLine($"TOTAL SHIPMENT FREIGHT WEIGHT: {masterCrate.CalculateWeight()} kg");
        // Calculation: 1.5 (Crate) + 2.2 (Laptop) + [0.2 (Box) + 0.15 (Mouse) + 0.9 (Keyboard)] + 0.4 (Mug) = 5.35 kg
    }
}
Strategy Pattern (Multi-Modal Transit - Transport Booking )

When booking a trip, the core goal remains the same: get the user to their destination. However, the calculation logic for pricing and time changes dynamically based on the chosen vehicle type. Using the Strategy pattern, we can add new transit methods (like Scooters or Helicopters) later without changing the core booking engine.

1. The Strategy Interface

This defines the common contract that every transportation algorithm must fulfill.

// The 'Strategy' interface
public interface ITravelStrategy
{
    double CalculateFare(double distanceInKm);
    int CalculateDurationMinutes(double distanceInKm);
}

2. Concrete Strategies

Each class encapsulates the specific rules, speeds, and base rates for that unique mode of transport.

// Concrete Strategy A: Cab (High price, dependent on traffic)
public class CabStrategy : ITravelStrategy
{
    public double CalculateFare(double distance) => 5.00 + (distance * 1.50); // $5 base + $1.50/km
    public int CalculateDurationMinutes(double distance) => (int)(distance * 3); // ~3 mins per km
}

// Concrete Strategy B: Bike (Low price, unaffected by traffic jams)
public class BikeStrategy : ITravelStrategy
{
    public double CalculateFare(double distance) => 1.00 + (distance * 0.40); // $1 base + $0.40/km
    public int CalculateDurationMinutes(double distance) => (int)(distance * 5); // ~5 mins per km
}

// Concrete Strategy C: Metro Train (Fixed pricing tiers, very fast)
public class MetroStrategy : ITravelStrategy
{
    public double CalculateFare(double distance) => distance < 10 ? 2.50 : 4.50; // Flat tier pricing
    public int CalculateDurationMinutes(double distance) => (int)(distance * 1.5) + 5; // Fast, but includes station waiting time
}

// Concrete Strategy D: Bus (Economy price, scheduled stops)
public class BusStrategy : ITravelStrategy
{
    public double CalculateFare(double distance) => 2.00; // Flat fare regardless of distance
    public int CalculateDurationMinutes(double distance) => (int)(distance * 4) + 10; // Slower due to routine stops
}

3. The Context Class

The TripBookingEngine manages the trip's metadata and utilizes the currently selected travel strategy to give the user dynamic updates.

// The 'Context'
public class TripBookingEngine
{
    private readonly double _distanceInKm;
    private ITravelStrategy _travelStrategy;

    public TripBookingEngine(double distanceInKm)
    {
        _distanceInKm = distanceInKm;
    }

    // Change strategy at runtime when the user clicks a different vehicle icon
    public void SetTravelMode(ITravelStrategy travelStrategy)
    {
        _travelStrategy = travelStrategy;
    }

    public void DisplayTripQuote()
    {
        if (_travelStrategy == null)
        {
            throw new InvalidOperationException("Please select a mode of transport.");
        }

        double fare = _travelStrategy.CalculateFare(_distanceInKm);
        int duration = _travelStrategy.CalculateDurationMinutes(_distanceInKm);

        Console.WriteLine($"Mode: {_travelStrategy.GetType().Name.Replace("Strategy", "")}");
        Console.WriteLine($"Est. Travel Time: {duration} mins");
        Console.WriteLine($"Total Cost: ${fare:F2}");
    }
}

4. Client Code Execution

Simulating a user switching tabs on a mobile app to compare different options for a 12-kilometer journey.

class Program
{
    static void Main()
    {
        double distanceToDestination = 12.0; // 12 km trip
        
        // Initialize booking engine for the route
        TripBookingEngine bookingApp = new TripBookingEngine(distanceToDestination);

        Console.WriteLine($"--- Route Options for a {distanceToDestination}km Trip ---\n");

        // 1. User checks Cab option
        bookingApp.SetTravelMode(new CabStrategy());
        bookingApp.DisplayTripQuote();
        Console.WriteLine(new string('-', 35));

        // 2. User checks Metro Train option
        bookingApp.SetTravelMode(new MetroStrategy());
        bookingApp.DisplayTripQuote();
        Console.WriteLine(new string('-', 35));

        // 3. User checks economic Bus option
        bookingApp.SetTravelMode(new BusStrategy());
        bookingApp.DisplayTripQuote();
        Console.WriteLine(new string('-', 35));
        
        // 4. User checks a Bike option
        bookingApp.SetTravelMode(new BikeStrategy());
        bookingApp.DisplayTripQuote();
    }
}
Observer Pattern Example (Back-in-Stock Reminder - E-Commerce)

When a popular item sells out, customers want to be alerted the moment inventory returns. By using the Observer Pattern, the product object keeps a list of customer emails. When a restock occurs, it loops through that list to send alerts, then clears the list since the event has passed.

1. The Observer Interface

This defines the interface for the subscribers waiting for the stock alert.

// The 'Observer' interface
public interface ICustomerObserver
{
    string Email { get; }
    void Update(string productName);
}

2. The Concrete Observer (Customer)

Each customer instance tracks their email and defines how they want to handle the alert notification.

// Concrete Observer
public class Customer : ICustomerObserver
{
    public string Name { get; }
    public string Email { get; }

    public Customer(string name, string email)
    {
        Name = name;
        Email = email;
    }

    public void Update(string productName)
    {
        Console.WriteLine($"[Email Sent to {Email}]: Hi {Name}! '{productName}' is back in stock! Order now before it sells out again.");
    }
}

3. The Subject (The Product)

The product class maintains its current stock level and an internal list of waiting customers.

// The 'Subject'
public class Product
{
    public string Name { get; }
    private int _stockLevel = 0;
    private readonly List<ICustomerObserver> _waitingCustomers = new List<ICustomerObserver>();

    public Product(string name)
    {
        Name = name;
    }

    // Equivalent to clicking the "Notify Me When Available" button
    public void RegisterForRestockAlert(ICustomerObserver customer)
    {
        if (!_waitingCustomers.Contains(customer))
        {
            _waitingCustomers.Add(customer);
            Console.WriteLine($"System: {customer.Email} subscribed to alerts for '{Name}'.");
        }
    }

    public void RemoveRestockAlert(ICustomerObserver customer)
    {
        _waitingCustomers.Remove(customer);
    }

    // Restock method that updates inventory and triggers notifications if items become available
    public void Restock(int newInventoryCount)
    {
        _stockLevel += newInventoryCount;
        Console.WriteLine($"\nLogistics: '{Name}' has been restocked with {newInventoryCount} units. Total Stock: {_stockLevel}");

        if (_stockLevel > 0)
        {
            NotifyWaitingCustomers();
        }
    }

    // Broadcast notifications to all observers on the list
    private void NotifyWaitingCustomers()
    {
        Console.WriteLine($"System: Pushing alerts to all {_waitingCustomers.Count} subscribers...\n");
        
        // Loop backwards or copy list if observers will unsubscribe immediately upon notification
        var subscribers = new List<ICustomerObserver>(_waitingCustomers);
        foreach (var customer in subscribers)
        {
            customer.Update(Name);
            _waitingCustomers.Remove(customer); // Remove them since they've been notified
        }
    }
}

4. Client Code Execution

Simulating multiple users joining a waitlist for a sold-out next-gen gaming console, followed by a warehouse shipment delivery.

class Program
{
    static void Main()
    {
        // 1. Create a highly demanded, out-of-stock product
        Product playstation = new Product("PlayStation 5 Pro");

        // 2. Create customer profiles
        ICustomerObserver customer1 = new Customer("Alice", "alice@email.com");
        ICustomerObserver customer2 = new Customer("Bob", "bob@example.com");
        ICustomerObserver customer3 = new Customer("Charlie", "charlie@gmail.com");

        Console.WriteLine("--- Users Sign Up For In-Stock Alerts ---");
        // 3. Customers sign up via the e-commerce UI
        playstation.RegisterForRestockAlert(customer1);
        playstation.RegisterForRestockAlert(customer2);
        playstation.RegisterForRestockAlert(customer3);

        Console.WriteLine("\n-----------------------------------------");

        // 4. Time passes... a shipment arrives at the fulfillment center
        // This automatically triggers the alerts to fire
        playstation.Restock(15);
        
        Console.WriteLine("\n-----------------------------------------");
        
        // 5. A late customer signs up after the reset
        ICustomerObserver customer4 = new Customer("Diana", "diana@outlook.com");
        playstation.RegisterForRestockAlert(customer4);
    }
}
Command Pattern with Queue (Education Example)

Definition

Encapsulates a request as an object, allowing it to be queued, logged, or executed later. Useful for asynchronous processing in systems like education portals.

Description

In an education system, students submit assignments online. Each submission is encapsulated as a command and placed into a queue. The system processes these commands in order, ensuring fairness and reliability.

Real-Time Example: Students Submitting Assignments


// Command interface
public interface ICommand
{
    void Execute();
}

// Concrete command: Submit Assignment
public class SubmitAssignmentCommand : ICommand
{
    private string _studentName;
    private string _assignment;

    public SubmitAssignmentCommand(string studentName, string assignment)
    {
        _studentName = studentName;
        _assignment = assignment;
    }

    public void Execute()
    {
        Console.WriteLine($"{_studentName} submitted {_assignment}");
    }
}

// Queue (Invoker)
public class AssignmentQueue
{
    private Queue _commands = new Queue();

    public void Enqueue(ICommand command)
    {
        _commands.Enqueue(command);
        Console.WriteLine("Assignment queued.");
    }

    public void ProcessAll()
    {
        Console.WriteLine("\nProcessing assignments in order...");
        while (_commands.Count > 0)
        {
            var cmd = _commands.Dequeue();
            cmd.Execute();
        }
    }
}

// Client
class Program
{
    static void Main()
    {
        AssignmentQueue queue = new AssignmentQueue();

        // Students submit assignments asynchronously
        queue.Enqueue(new SubmitAssignmentCommand("Alice", "Math Homework"));
        queue.Enqueue(new SubmitAssignmentCommand("Bob", "Science Project"));
        queue.Enqueue(new SubmitAssignmentCommand("Charlie", "History Essay"));

        // Later, the system processes them in order
        queue.ProcessAll();
    }
}

Interview Insight

  • Queue ensures assignments are processed in the order they were submitted.
  • Command encapsulates each submission, making it reusable and easy to log.
  • In real systems, this pattern maps to message queues like Azure Service Bus, RabbitMQ, or Kafka.

Mediator Pattern Example (Classroom Chat Room)

Definition

The Mediator Design Pattern defines an object that encapsulates how a set of objects interact. This pattern promotes loose coupling by keeping objects from referring to each other explicitly, allowing their interactions to be modified independently.

How this Classroom Chat Fits the Pattern

  • The Mediator (IChatRoomMediator): The communication contract that defines how users register with a room and send messages.
  • The Concrete Mediator (ClassroomChatServer): The central chat server hub. It maintains a dictionary list of all connected students and teachers, managing the routing rules of who receives what text message.
  • The Colleagues (User): The human participants (Students or Teachers). They only know their own name and their central chat mediator. They never hold references to their classmates' objects.

1. The Mediator Interface

This defines the methods required to manage participants and broadcast communications.

// The 'Mediator' interface
public interface IChatRoomMediator
{
    void RegisterUser(User user);
    void SendMessage(string message, User sender);
}

2. The Base Colleague Component

This represents a abstract participant in the school portal chat system.

// The 'Colleague' abstract base
public abstract class User
{
    protected IChatRoomMediator _chatMediator;
    public string Name { get; }

    public User(IChatRoomMediator chatMediator, string name)
    {
        _chatMediator = chatMediator;
        Name = name;
    }

    public abstract void Receive(string from, string message);
}

3. Concrete Colleague Components

These represent the real roles in the system. Notice that sending a message doesn't target a specific person; it is simply passed up to the mediator engine.

// Concrete Colleague A: Student Participant
public class StudentUser : User
{
    public StudentUser(IChatRoomMediator mediator, string name) : base(mediator, name) { }

    public void Send(string message)
    {
        Console.WriteLine($"\n[UI Action] Student '{Name}' types: \"{message}\"");
        _chatMediator.SendMessage(message, this); // Delegate to mediator
    }

    public override void Receive(string from, string message)
    {
        Console.WriteLine($"[{Name}'s Screen] Chat from {from}: {message}");
    }
}

// Concrete Colleague B: Teacher Participant
public class TeacherUser : User
{
    public TeacherUser(IChatRoomMediator mediator, string name) : base(mediator, name) { }

    public void Send(string message)
    {
        Console.WriteLine($"\n[UI Action] Teacher **{Name}** announces: \"{message}\"");
        _chatMediator.SendMessage(message, this); // Delegate to mediator
    }

    public override void Receive(string from, string message)
    {
        Console.WriteLine($"[Teacher {Name}'s Screen] Chat from {from}: {message}");
    }
}

4. The Concrete Mediator (The Chat Server)

This central point holds the master list of active connections and dynamically loops through them to broadcast text updates.

// The 'Concrete Mediator'
public class ClassroomChatServer : IChatRoomMediator
{
    private readonly List<User> _connectedUsers = new List<User>();

    public void RegisterUser(User user)
    {
        if (!_connectedUsers.Contains(user))
        {
            _connectedUsers.Add(user);
            Console.WriteLine($"System Log: '{user.Name}' joined the live classroom chat.");
        }
    }

    // Central distribution: When someone sends a message, loop and update everyone else
    public void SendMessage(string message, User sender)
    {
        foreach (var user in _connectedUsers)
        {
            // Don't send the message back to the person who typed it!
            if (user != sender)
            {
                user.Receive(sender.Name, message);
            }
        }
    }
}

5. Client Code Execution

Simulating a teacher starting an online lecture session and interacting with students inside a unified chat channel.

Template Method Pattern - (Online Exam Process)

Definition

Defines the skeleton of an algorithm in a base class, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps without changing the overall algorithm’s structure.

Description

Use the Template Method Pattern when you want to enforce a fixed sequence of steps in an algorithm, but allow subclasses to customize specific parts. It promotes code reuse and consistency across variations of the process.

Real-Time Example: Online Exam Process


// Abstract class (Template)
public abstract class OnlineExam
{
    // Template method
    public void ConductExam()
    {
        Login();
        StartExam();
        EvaluateAnswers();
        ShowResult();
    }

    protected abstract void Login();
    protected abstract void StartExam();
    protected abstract void EvaluateAnswers();

    // Common step
    protected void ShowResult()
    {
        Console.WriteLine("Result displayed to student.");
    }
}

// Concrete classes
public class MathExam : OnlineExam
{
    protected override void Login()
    {
        Console.WriteLine("Math student logged in.");
    }

    protected override void StartExam()
    {
        Console.WriteLine("Math exam started.");
    }

    protected override void EvaluateAnswers()
    {
        Console.WriteLine("Math answers evaluated.");
    }
}

public class ScienceExam : OnlineExam
{
    protected override void Login()
    {
        Console.WriteLine("Science student logged in.");
    }

    protected override void StartExam()
    {
        Console.WriteLine("Science exam started.");
    }

    protected override void EvaluateAnswers()
    {
        Console.WriteLine("Science answers evaluated.");
    }
}

// Client
class Program

CQRS Design Pattern with MediatR

Definition

CQRS (Command Query Responsibility Segregation) is an architectural pattern that separates read operations (queries) from write operations (commands).

  • Command side → Handles state changes (create, update, delete).
  • Query side → Optimized for reading data.

Benefits: Scalability, flexibility (different models for reads vs writes), and clear separation of concerns.

MediatR and IMediator

IMediator is an interface provided by the MediatR NuGet package. It is not part of your own code — you install it and register it in dependency injection.

  1. Install NuGet packages: 
    dotnet add package MediatR
dotnet add package MediatR.Extensions.Microsoft.DependencyInjection
  2. Register MediatR in Program.cs: 
    builder.Services.AddMediatR(cfg => 
    cfg.RegisterServicesFromAssembly(typeof(Program).Assembly));
  3. Inject into your controller: 
    private readonly IMediator _mediator;
public StudentsController(IMediator mediator)
{
    _mediator = mediator;
}

The IMediator interface provides methods like Send() and Publish() to dispatch commands, queries, and notifications to their handlers.

Code Example (C# with MediatR)


// Command: Create a new student
public record CreateStudentCommand(string Name, int Age) : IRequest;

// Command Handler
public class CreateStudentHandler : IRequestHandler
{
    public Task Handle(CreateStudentCommand cmd, CancellationToken ct)
    {
        var student = new Student { Id = Guid.NewGuid(), Name = cmd.Name, Age = cmd.Age };
        // Save to DB (write side)
        return Task.FromResult(new StudentResult(student.Id, "Created"));
    }
}

// Query: Get student by Id
public record GetStudentQuery(Guid Id) : IRequest;

// Query Handler
public class GetStudentHandler : IRequestHandler
{
    public Task Handle(GetStudentQuery query, CancellationToken ct)
    {
        // Fetch from DB (read side)
        return Task.FromResult(new Student { Id = query.Id, Name = "Alice", Age = 20 });
    }
}

// Controller
[ApiController]
[Route("api/students")]
public class StudentsController : ControllerBase
{
    private readonly IMediator _mediator;
    public StudentsController(IMediator mediator) => _mediator = mediator;

    [HttpPost]
    public async Task Create(CreateStudentCommand cmd)
    {
        var result = await _mediator.Send(cmd);
        return Ok(result);
    }

    [HttpGet("{id}")]
    public async Task Get(Guid id)
    {
        var student = await _mediator.Send(new GetStudentQuery(id));
        return Ok(student);
    }
}

// Result DTO
public record StudentResult(Guid Id, string Status);
public class Student { public Guid Id { get; set; } public string Name { get; set; } public int Age { get; set; } }

Takeaway

  • Commands → Change system state (writes).
  • Queries → Retrieve data (reads).
  • MediatR → Decouples controllers from handlers using IMediator.
OOP Concepts

1. Abstraction

Hiding implementation details, showing only essential features.


abstract class Shape {
    public abstract double Area();
}
class Circle : Shape {
    public double Radius { get; set; }
    public override double Area() => Math.PI * Radius * Radius;
}

Memory hook: Abstract = show what, hide how.

2. Encapsulation

Wrapping data (fields) and behavior (methods) together inside a class. Protects data and controls access.


class BankAccount {
    private decimal balance; // hidden data
    public void Deposit(decimal amount) => balance += amount;
    public decimal GetBalance() => balance; // controlled access
}

Memory hook: Capsule = protect + control access.

3. Inheritance

One class derives from another, reusing its properties and methods.


class Animal {
    public void Eat() => Console.WriteLine("Eating...");
}
class Dog : Animal {
    public void Bark() => Console.WriteLine("Barking...");
}

Memory hook: Inheritance = reuse parent features.

4. Polymorphism

Same interface, different implementations. Two main types:

  • Compile-time (Overloading): Same method name, different signatures.
  • Runtime (Overriding): Subclass changes base method behavior.

class Shape {
    public virtual void Draw() => Console.WriteLine("Drawing shape");
}
class Circle : Shape {
    public override void Draw() => Console.WriteLine("Drawing circle");
}

Memory hook: Poly = many forms.

Polymorphism Types

1. Compile-time Polymorphism (Static Binding)

Achieved via method overloading or operator overloading. Decided at compile time.


class Calculator {
    public int Add(int a, int b) => a + b;
    public double Add(double a, double b) => a + b;
}

2. Runtime Polymorphism (Dynamic Binding)

Achieved via method overriding using virtual/override. Decided at runtime.


class Animal {
    public virtual void Speak() => Console.WriteLine("Animal sound");
}
class Dog : Animal {
    public override void Speak() => Console.WriteLine("Bark");
}

3. Interface Polymorphism

Multiple classes implement the same interface differently.


interface IPayment { void Pay(decimal amount); }
class CreditCard : IPayment {
    public void Pay(decimal amount) => Console.WriteLine($"Paid {amount} via Credit Card");
}
class PayPal : IPayment {
    public void Pay(decimal amount) => Console.WriteLine($"Paid {amount} via PayPal");
}

4. Polymorphism with Inheritance Levels

  • Single Inheritance: One base → one derived (Animal → Dog).
  • Multilevel Inheritance: Chain of classes (LivingBeing → Animal → Dog).
  • Hierarchical Inheritance: Multiple derived classes from one base (Shape → Circle, Rectangle).
  • Hybrid: Combination of multilevel + interfaces (Employee : Person, IWorker).

Key Idea: Runtime polymorphism shines in inheritance chains — same base call, different derived outputs.
