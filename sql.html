Beginner SQL Interview Questions & Answers
# Question Answer
1 Difference between DELETE, TRUNCATE, DROP DELETE: Removes rows, can use WHERE, logged, rollback possible.
TRUNCATE: Removes all rows, faster, minimal logging, resets identity.
DROP: Removes entire table (structure + data).
2 Primary Key vs Unique Key vs Foreign Key Primary Key: Unique, no NULLs, one per table.
Unique Key: Ensures uniqueness, allows one NULL, multiple per table.
Foreign Key: Enforces referential integrity.
3 WHERE vs HAVING WHERE: Filters rows before grouping.
HAVING: Filters groups after aggregation.
4 INNER JOIN vs LEFT JOIN vs FULL JOIN INNER JOIN: Matching rows only.
LEFT JOIN: All rows from left + matches.
FULL JOIN: All rows from both sides.
5 Second Highest Salary Query SELECT MAX(salary)
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
6 Find Duplicate Records SELECT column_name, COUNT(*)
FROM table_name
GROUP BY column_name
HAVING COUNT(*) > 1;
7 Subquery vs CTE Subquery: Nested inline.
CTE: Defined with WITH, reusable, supports recursion.
8 GROUP BY & Aggregates Groups rows and applies aggregate functions.
SELECT department, AVG(salary)
FROM employees
GROUP BY department;
9 CHAR vs VARCHAR CHAR(n): Fixed length, pads with spaces.
VARCHAR(n): Variable length, saves space.
10 NULL Handling Use IS NULL / IS NOT NULL.
Replace with COALESCE() or ISNULL().
Example: SELECT COALESCE(middle_name, 'N/A') FROM employees;
Intermediate SQL Interview Questions & Answers
# Question Answer
11 Clustered vs Non‑Clustered Index Clustered: Sorts and stores data rows physically, one per table.
Non‑Clustered: Separate structure with pointers to data, multiple allowed.
Example: Clustered on OrderID, Non‑Clustered on CustomerID.
12 Covering Index An index that contains all columns needed by a query, avoiding lookups.
Example: CREATE INDEX idx_orders ON Orders(CustomerID, OrderDate, TotalAmount).
13 Query Execution Plan Shows how SQL Server executes a query (scans, seeks, joins).
Used to identify bottlenecks like table scans or missing indexes.
14 UNION vs UNION ALL UNION: Removes duplicates, adds sorting overhead.
UNION ALL: Keeps duplicates, faster.
Example: Reporting queries often use UNION ALL for performance.
15 Window Functions Functions like ROW_NUMBER(), RANK(), DENSE_RANK().
Example: SELECT Name, Salary, RANK() OVER (ORDER BY Salary DESC) AS Rank
FROM Employees;
16 Nth Highest Salary SELECT Salary FROM (SELECT Salary, DENSE_RANK() OVER (ORDER BY Salary DESC) AS rnk
FROM Employees) t WHERE rnk = N;
17 Transactions & ACID Ensures Atomicity, Consistency, Isolation, Durability.
Example: Bank transfer = debit + credit in one transaction.
18 Isolation Levels Read Uncommitted: Dirty reads.
Read Committed: Prevents dirty reads.
Repeatable Read: Prevents non‑repeatable reads.
Serializable: Prevents phantom reads, strictest.
19 Deadlocks Occur when two transactions wait on each other’s locks.
Prevention: Consistent locking order, shorter transactions, use WITH (NOLOCK) carefully.
20 Optimistic vs Pessimistic Locking Optimistic: Assume no conflict, check at commit.
Pessimistic: Lock resources immediately.
Example: High‑concurrency systems prefer optimistic.
21 Partitioning Splits large tables into smaller partitions for performance.
Example: Partition sales data by year.
22 Sharding vs Partitioning Partitioning: Within one DB instance.
Sharding: Across multiple DB servers.
Example: Global apps shard by region.
23 Materialized Views Precomputed query results stored physically.
Speeds up reporting but needs refresh.
Example: Monthly sales summary.
24 OLTP vs OLAP Schema OLTP: Normalized, fast inserts/updates.
OLAP: Denormalized, star/snowflake schema for analytics.
25 Audit Logging Track changes for compliance.
Example: Use triggers to insert into AuditLog table on UPDATE/DELETE.
Advanced SQL Interview Questions & Answers
# Question Answer
26 Schema for Ride‑Sharing App Tables: Drivers, Riders, Trips, Payments.
Example: Trips table links DriverID, RiderID, StartLocation, EndLocation, Fare.
27 Scaling Queries for 200M Row Orders Table Use partitioning by date, indexes on CustomerID/OrderDate, and covering indexes.
Example: CREATE INDEX idx_orders ON Orders(CustomerID, OrderDate).
28 Fact & Dimension Tables Fact: Transactional data (Sales, Orders).
Dimension: Descriptive attributes (Customer, Product, Time).
Example: Star schema for sales reporting.
29 Troubleshooting Slow Query Steps: Check execution plan → Index usage → Statistics → Locks → Hardware bottlenecks.
Example: Add missing index to avoid table scan.
30 Index Fragmentation Caused by frequent inserts/updates.
Fix: ALTER INDEX REBUILD or ALTER INDEX REORGANIZE.
31 Heap vs Clustered Tables Heap: No clustered index, unordered.
Clustered: Ordered by clustered key.
Example: Heap for staging, clustered for production.
32 Soft Deletes Add IsDeleted BIT column instead of removing rows.
Example: UPDATE Users SET IsDeleted = 1 WHERE UserID = 10;
33 Change Data Capture (CDC) Tracks inserts/updates/deletes for auditing or ETL.
Example: Enable CDC on Orders table for downstream reporting.
34 Replication vs Log Shipping Replication: Real‑time copy for reporting.
Log Shipping: Periodic backup/restore for disaster recovery.
35 Data Consistency Across Microservices Use distributed transactions, event sourcing, or outbox pattern.
Example: Outbox table ensures reliable message publishing.
36 CQRS Pattern Separate Command (writes) and Query (reads).
Example: Commands update DB, Queries use read‑optimized schema.
37 Multi‑Tenant Database Approaches: Shared schema with TenantID, separate schema per tenant, or separate DB per tenant.
Example: SaaS apps often use TenantID column.
38 Horizontal vs Vertical Scaling Horizontal: Add more servers (sharding).
Vertical: Increase server resources (CPU, RAM).
39 Securing Sensitive Data Use encryption (TDE, Always Encrypted), masking, and role‑based access.
Example: Encrypt SSN column.
40 Row‑Level Security Restrict access based on user context.
Example: Sales reps see only their region’s data.
41 High Availability in SQL Server Options: Failover clustering, AlwaysOn Availability Groups, Log Shipping.
Example: AlwaysOn for mission‑critical apps.
42 Temp Tables vs Table Variables Temp Tables: Support indexes, statistics, better for large sets.
Table Variables: In‑memory, lightweight, no stats.
43 Large Batch Inserts Use BULK INSERT, BCP, or batching with transactions.
Example: Insert 10k rows per batch.
44 Query Hints Force optimizer behavior (e.g., OPTION (FORCE INDEX)).
Use cautiously, only when optimizer misbehaves.
45 Monitoring SQL Server Performance Tools: Profiler, Extended Events, DMVs.
Example: DMV query for top CPU‑consuming queries.
46 Index Seek vs Index Scan Seek: Efficient, uses index key.
Scan: Reads entire index/table.
Example: Seek on WHERE CustomerID = 100.
47 Schema for Event Sourcing Store events instead of state.
Example: Orders table replaced by Events table (OrderCreated, OrderShipped).
48 Denormalization Add redundancy for performance.
Example: Store CustomerName in Orders table to avoid join.
49 Legacy Database Migration
  • Assessment: Analyze existing schema, dependencies, and data quality.
  • ETL Process: Extract, Transform, Load using tools like SSIS or custom scripts.
  • Validation: Compare row counts, checksums, and sample queries to ensure accuracy.
  • Optimization: Add indexes, constraints, and normalize/denormalize as needed.
  • Rollback Plan: Always prepare backups and rollback scripts before migration.

Example: Use SQL Server Integration Services (SSIS) to migrate data from Oracle to SQL Server, applying transformations during the load.
50 Best Practices for Schema Versioning in Enterprise Systems
  • Use Version Control: Keep all schema changes in source control (e.g., Git).
  • Migration Scripts: Apply changes via incremental scripts (CREATE/ALTER), not manual edits.
  • Automated Deployment: Use CI/CD pipelines to apply schema changes consistently.
  • Backward Compatibility: Ensure changes don’t break existing applications (e.g., add columns instead of dropping).
  • Documentation: Maintain clear change logs for auditing and rollback.
  • Testing: Validate schema changes in staging before production.

Example: Use tools like Flyway or Liquibase to manage schema migrations with version tags.
