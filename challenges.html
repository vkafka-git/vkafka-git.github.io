How would you implement retry logic and resilience in a .NET microservice calling external APIs?

Situation: A .NET microservice depends on external APIs that can be slow, rate-limited, or temporarily unavailable, risking cascading failures.

Approach:

  • Retry with Exponential Backoff: Use Polly to retry transient failures (timeouts, 5xx, 429). 
    var retryPolicy = Policy
  .Handle<HttpRequestException>()
  .OrResult<HttpResponseMessage>(r => !r.IsSuccessStatusCode)
  .WaitAndRetryAsync(3, attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt)));
  • Circuit Breaker: Prevent repeated calls to an unhealthy API. 
    var circuitBreaker = Policy
  .Handle<HttpRequestException>()
  .CircuitBreakerAsync(5, TimeSpan.FromSeconds(30));
  • Fallbacks: Provide cached/default data if the API is unavailable.
  • Bulkhead Isolation: Limit concurrent calls to avoid resource exhaustion.
  • Timeouts: Always set request timeouts (e.g., 10 seconds).
  • Resiliency at Scale: Use message queues (Azure Service Bus, RabbitMQ) to decouple user requests from external API calls. For long workflows, apply Saga pattern for consistency.

Result: With retry, circuit breaker, fallback, bulkhead, and timeout policies, the microservice becomes resilient. Even if the external API is down, the system fails gracefully, recovers automatically, and avoids cascading failures.

Interview Summary:
“I’d implement resilience in a .NET microservice using Polly for retry with exponential backoff, circuit breaker to fail fast, and fallback for cached/default responses. How would you process 1000 tasks in parallel in .NET while limiting concurrency to 10 at a time?

Situation: A .NET application needs to process 1000 tasks in parallel, but we must limit concurrency to 10 tasks at a time to avoid overwhelming resources.

Approach:

  • SemaphoreSlim: Use a SemaphoreSlim to restrict the number of concurrent tasks. 
    var semaphore = new SemaphoreSlim(10); // limit to 10
var tasks = new List<Task>();

foreach (var item in items)
{
    await semaphore.WaitAsync();
    tasks.Add(Task.Run(async () =>
    {
        try
        {
            await ProcessItemAsync(item);
        }
        finally
        {
            semaphore.Release();
        }
    }));
}

await Task.WhenAll(tasks);
  • Parallel.ForEachAsync (NET 6+): Use built-in parallelism with a degree of parallelism. 
    await Parallel.ForEachAsync(items,
    new ParallelOptions { MaxDegreeOfParallelism = 10 },
    async (item, token) =>
    {
        await ProcessItemAsync(item);
    });
  • TPL Dataflow: Use ActionBlock with MaxDegreeOfParallelism = 10 for advanced scenarios like pipelines.

Result: With concurrency limited to 10, the application processes all 1000 tasks efficiently without exhausting CPU, memory, or database connections.

  • Resilience & Scalability: - Use async/await to avoid blocking threads.
    - Apply retry logic for chunk failures.
    - Monitor uploads with Application Insights.
  • Content Delivery: - Serve downloads via CDN (Azure Front Door, CloudFront).
    - Avoid routing large files through the API itself.

Troubleshooting & Optimizing a Slow Multi-Join SQL Query

Situation: A SQL Server query with multiple joins is running very slowly. This can be due to poor indexing, inefficient join order, large intermediate result sets, or suboptimal query design.

Approach:

  • Examine Execution Plan: Use SET STATISTICS IO ON or EXPLAIN (Actual Execution Plan in SSMS) to identify table scans, expensive joins, and missing indexes.
  • Index Optimization: Ensure join columns and filter columns have appropriate indexes. Consider covering indexes for frequently queried combinations.
  • Join Order & Type: - Place selective filters early to reduce dataset size.
    - Use INNER JOINs only when necessary; LEFT JOINs can expand result sets.
    - Reorder joins to minimize intermediate row counts.
  • Reduce Data Volume: - Select only required columns (avoid SELECT *).
    - Apply WHERE filters before joins if possible.
    - Use CTEs or temp tables to pre-filter large datasets.
  • Statistics & Maintenance: Update table statistics and rebuild fragmented indexes to ensure the optimizer has accurate information.
  • Partitioning: For very large tables, consider partitioning to reduce scan size.
  • Query Rewrite: Replace correlated subqueries with joins, simplify complex expressions, and avoid unnecessary DISTINCT or ORDER BY clauses.
  • Parallelism & Hints: Allow SQL Server to use parallel execution. Use query hints cautiously (e.g., OPTION (HASH JOIN)) only after testing.

Result: By analyzing the execution plan, applying proper indexing, filtering early, and restructuring joins, the query performance improves significantly, often reducing execution time from minutes to seconds.

Interview Summary:
“To troubleshoot a slow multi-join query, I’d start with the execution plan to identify bottlenecks. Then I’d optimize indexes on join/filter columns, reduce data volume by selecting only needed fields, reorder joins, and update statistics. If needed, I’d use CTEs, partitioning, or query rewrites. This systematic approach usually improves performance drastically.”
Choosing Between CTE, Temp Table, and Table Variable

Situation: In SQL Server, you often need intermediate result sets when working with complex queries. Options include Common Table Expressions (CTEs), temporary tables, and table variables. Each has different performance and use-case implications.

Approach:

  • CTE (Common Table Expression):
    • Best for readability and modular query design.
    • Useful for recursion (e.g., hierarchical data).
    • Exists only during query execution; cannot be indexed or reused across queries.
    • Performance similar to inline views/subqueries.
  • Temp Table (#Temp):
    • Physically created in tempdb.
    • Can be indexed, constrained, and reused across multiple queries or stored procedures.
    • Better for large datasets and complex joins where performance tuning is needed.
    • Supports statistics, which helps the optimizer choose efficient plans.
  • Table Variable (@Table):
    • Stored in memory (but can spill to tempdb if large).
    • Good for small datasets (hundreds or a few thousand rows).
    • Limited support for indexing (only primary key/unique constraints).
    • Does not maintain statistics, so optimizer may assume 1 row, which can lead to poor plans for large data.
    • Scope limited to the batch or procedure.

Decision Guidelines:

  • Use CTE for readability, recursion, and one-off intermediate sets.
  • Use Temp Table for large datasets, complex joins, or when indexing/statistics are needed.
  • Use Table Variable for small datasets, lightweight operations, or when you don’t need statistics.

Result: Choosing the right option balances readability and performance. Temp tables are generally preferred for performance-critical scenarios, while CTEs and table variables are better for simplicity and small-scale operations.

Interview Summary:
“I decide based on dataset size and query complexity: CTEs for readability and recursion, temp tables for large datasets with indexing/statistics, and table variables for small, lightweight operations. This ensures both clarity and performance.”

Designing a Transaction Strategy for Multi-Table Inserts Without Deadlocks

Situation: You need to insert related data into multiple SQL Server tables (e.g., Customer, Orders, OrderDetails) while ensuring transactional consistency. The challenge is to avoid deadlocks when multiple transactions run concurrently.

Approach:

  • Consistent Resource Access Order: Always insert into tables in the same sequence (e.g., Customer → Orders → OrderDetails). This prevents circular waits that cause deadlocks.
  • Keep Transactions Short: Perform only necessary inserts inside the transaction. Do not include long-running queries or business logic.
  • Use Proper Isolation Level: - Default READ COMMITTED is usually sufficient.
    - For bulk inserts, consider READ COMMITTED SNAPSHOT to reduce locking contention.
  • Batch Inserts: Insert data in manageable batches (e.g., 10k rows per transaction) instead of one massive transaction.
  • Locking Hints (if needed): Use UPDLOCK or ROWLOCK to control lock granularity and avoid escalation to table locks.
  • Stored Procedure Encapsulation: Encapsulate multi-table insert logic in a stored procedure with explicit BEGIN TRANSACTION / COMMIT / ROLLBACK handling. 
    BEGIN TRANSACTION;
BEGIN TRY
    INSERT INTO Customer (...) VALUES (...);
    INSERT INTO Orders (...) VALUES (...);
    INSERT INTO OrderDetails (...) VALUES (...);
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;
    -- Log error
END CATCH;
  • Index & Foreign Key Strategy: Ensure foreign keys and indexes exist to speed up inserts and reduce lock duration.
  • Monitoring: Use SQL Server Profiler or Extended Events to detect deadlocks and confirm that the chosen strategy eliminates them.

Result: By enforcing a consistent insert order, keeping transactions short, batching operations, and using appropriate isolation levels, you achieve transactional consistency across multiple tables while minimizing the risk of deadlocks.

“To insert into multiple tables without deadlocks, I’d use a transaction with a consistent table access order, keep it short, batch inserts, and apply proper isolation levels. I’d encapsulate the logic in a stored procedure with error handling. This ensures both consistency and concurrency safety.”
Handling Concurrent Updates in SQL Server

Situation: Two users attempt to update the same record at the same time. Without proper concurrency control, one user’s changes may overwrite the other’s, leading to lost updates or inconsistent data.

Approach:

  • Pessimistic Concurrency (Locking):
    • Use transactions with row-level locks (WITH (UPDLOCK, ROWLOCK)).
    • Ensures only one user can update the record at a time.
    • Best for high-contention scenarios but can reduce scalability.
  • Optimistic Concurrency (RowVersion/Timestamp):
    • Add a rowversion column to the table.
    • When updating, check if the rowversion matches the one originally read.
    • If it has changed, another user updated the record → reject or retry update.
    • Best for low-contention, high-scalability scenarios.
    UPDATE Customers
SET Name = @Name
WHERE CustomerId = @CustomerId
AND RowVersion = @OriginalRowVersion;
  • Application-Level Handling:
    • Catch concurrency exceptions in the application.
    • Decide on conflict resolution strategy:
      • Client Wins: Last user’s changes overwrite.
      • Store Wins: Reject conflicting update.
      • Merge: Combine changes intelligently.

Result: By using rowversion-based optimistic concurrency or transaction-level locking, SQL Server ensures data integrity. The application can then decide how to resolve conflicts when simultaneous updates occur.

Interview Summary:
“If two users try to update the same record, I’d use optimistic concurrency with a rowversion column. SQL Server detects conflicts, and the application decides whether to retry, reject, or merge changes. For high-contention cases, I’d use transactions with locking. This ensures consistency without lost updates.”
Deciding Which Columns to Index in a Large Transactional Table

Situation: In a large transactional table (millions of rows, frequent inserts/updates), indexing decisions directly affect query performance and write overhead. The challenge is to balance read efficiency with write cost.

Approach:

  • Primary Key / Clustered Index:

  • Foreign Keys:

  • Frequently Queried Columns:
    • Columns used in WHERE, JOIN, GROUP BY, and ORDER BY clauses.

    • Include additional columns in non-clustered indexes to cover queries and avoid lookups.

    • Limit indexes to those that provide measurable query performance benefits.

Clustered vs. Non‑Clustered Indexes in SQL Server

Situation: SQL Server offers two main types of indexes: clustered and non‑clustered. Choosing between them depends on how data is accessed, stored, and queried.

Clustered Index:

  • Physically sorts and stores rows in the table based on the index key.
  • Each table can have only one clustered index because rows can only be ordered one way.
  • Best for:
    • Primary keys or unique identifiers.
    • Range queries (e.g., WHERE OrderDate BETWEEN ...).
    • Columns frequently used for sorting or sequential access.
  • Example: 
    CREATE CLUSTERED INDEX idx_orders_orderid
ON Orders(OrderID);

Non‑Clustered Index:

  • Creates a separate structure with pointers (row locators) to the actual data rows.
  • Multiple non‑clustered indexes can exist on a table.
  • Best for:
    • Columns used in WHERE, JOIN, GROUP BY, ORDER BY.
    • Covering queries by including extra columns (INCLUDE).
    • Improving point lookups and selective filters.
  • Example: 
    CREATE NONCLUSTERED INDEX idx_orders_customer
ON Orders(CustomerID)
INCLUDE (OrderDate, TotalAmount);

How to Choose:

  • Use a clustered index for the table’s natural ordering (usually the primary key or a column used in range queries).
  • Use non‑clustered indexes to optimize specific query patterns (filters, joins, lookups).
  • Balance performance: too many non‑clustered indexes slow down INSERT/UPDATE/DELETE.
  • Analyze execution plans and DMVs to confirm index effectiveness.

Result: Clustered indexes define the physical order of data and are ideal for primary keys and range queries, while non‑clustered indexes provide flexible, query‑specific optimization. Choosing depends on query patterns and workload balance.

Interview Summary:
“Clustered indexes store rows physically ordered by the key, best for primary keys and range queries. Non‑clustered indexes are separate structures with pointers, best for filters, joins, and covering queries. I choose clustered for natural ordering and non‑clustered for query optimization, balancing read speed with write overhead.”
Using Covering Indexes to Improve Query Performance

Situation: Queries that frequently access large tables can become slow if SQL Server must perform extra lookups to fetch non-indexed columns. A covering index solves this by including all columns needed for the query, so SQL Server can satisfy it directly from the index.

Approach:

  • Definition: A covering index is a non-clustered index that “covers” a query by including all columns referenced in SELECT, WHERE, JOIN, and ORDER BY.
  • How It Helps:
    • Eliminates key lookups (extra trips to the base table).
    • Reduces I/O since all needed data is in the index structure.
    • Improves performance for frequently executed queries.
  • Example: 
    -- Query
SELECT CustomerID, OrderDate, TotalAmount
FROM Orders
WHERE CustomerID = 123;

-- Covering Index
CREATE NONCLUSTERED INDEX idx_orders_customer
ON Orders(CustomerID)
INCLUDE (OrderDate, TotalAmount);

    ✅ This index covers the query completely, avoiding lookups to the clustered index.

  • Best Practices:
    • Use INCLUDE for non-key columns to keep index size smaller.
    • Cover queries that run frequently and are performance-critical.
    • Avoid over-indexing — each index adds overhead to INSERT/UPDATE/DELETE.
    • Monitor with DMVs (sys.dm_db_missing_index_details) to identify queries that would benefit.

Result: Covering indexes allow SQL Server to serve queries directly from the index, eliminating costly lookups and significantly improving performance on large transactional tables.

Interview Summary:
“I use covering indexes when a query frequently needs extra columns beyond the filter/join keys. By including those columns in the index, SQL Server avoids lookups, reducing I/O and speeding up execution. I balance this with write overhead to avoid over-indexing.”
Error Handling in a Stored Procedure with Multi‑Table Inserts

Situation: A stored procedure must insert related data into multiple SQL Server tables (e.g., Customer, Orders, OrderDetails). If any insert fails, the entire operation should roll back to maintain consistency. Proper error handling ensures reliability and easier troubleshooting.

Approach:

  • Use Explicit Transactions: Wrap all inserts in a single transaction so they succeed or fail together.
  • TRY…CATCH Block: Handle errors gracefully by rolling back and logging the issue.
  • Error Logging: Insert error details into a logging table for later review.
  • Batch Strategy: If inserting large volumes, process in batches to reduce lock contention and improve reliability.
  • Validation: Validate input data before attempting inserts to reduce runtime errors.

Example Implementation:

CREATE PROCEDURE InsertOrderData
    @CustomerId INT,
    @CustomerName NVARCHAR(100),
    @OrderId INT,
    @OrderDate DATETIME,
    @ProductId INT,
    @Quantity INT
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRANSACTION;
    BEGIN TRY
        INSERT INTO Customer (CustomerId, Name)
        VALUES (@CustomerId, @CustomerName);

        INSERT INTO Orders (OrderId, CustomerId, OrderDate)
        VALUES (@OrderId, @CustomerId, @OrderDate);

        INSERT INTO OrderDetails (OrderId, ProductId, Quantity)
        VALUES (@OrderId, @ProductId, @Quantity);

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        ROLLBACK TRANSACTION;

        INSERT INTO ErrorLog (ErrorMessage, ErrorTime)
        VALUES (ERROR_MESSAGE(), GETDATE());

        THROW; -- re-raise error for caller
    END CATCH
END;

Best Practices:

  • Keep transactions short to minimize locking.
  • Always log errors with context (procedure name, parameters).
  • Use THROW instead of RAISERROR for modern error handling.
  • Test with concurrent inserts to ensure deadlock safety.

Result: With explicit transactions, TRY…CATCH, and error logging, the stored procedure ensures that either all inserts succeed together or none are applied, maintaining data integrity and providing clear diagnostics.

Interview Summary:
“I’d design error handling with a TRY…CATCH block inside a transaction. If any insert fails, rollback ensures consistency, and errors are logged for review. This guarantees reliability and makes troubleshooting easier.”
Handling Partial Bulk Insert Failures in SQL Server

Situation: You’re importing millions of rows into SQL Server using bulk insert or SqlBulkCopy. If the process fails halfway, you need to log failed rows and retry only those, without reprocessing successful ones.

Analyzing and Fixing Deadlocks in Production

Situation: A deadlock occurs when two or more transactions block each other by holding locks on resources the other needs. In production, this can cause query failures and impact application stability. The goal is to identify the root cause and implement a fix without disrupting operations.

Approach:

  • Capture Deadlock Information:
    • Enable SQL Server trace flags (1222 or 1204) to log deadlock details.
    • Use Extended Events or SQL Profiler to capture deadlock graphs.
    • Analyze the deadlock graph to see which queries and resources are involved.
  • Analyze Execution Plans:
    • Check the queries involved for inefficient joins, missing indexes, or large scans.
    • Identify lock types (row, page, table) and escalation patterns.
  • Fix Strategies:
    • Consistent Access Order: Ensure all transactions access tables in the same sequence to avoid circular waits.
    • Reduce Transaction Scope: Keep transactions short; avoid user interaction inside transactions.
    • Index Optimization: Add indexes to reduce lock contention by narrowing scans.
    • Isolation Level Tuning: Use READ COMMITTED SNAPSHOT to reduce locking conflicts.
    • Retry Logic: Implement retry with exponential backoff in application code for deadlock victims.
    • Batch Processing: Break large updates/inserts into smaller batches to minimize lock duration.
  • Monitoring & Prevention:
    • Set up alerts for deadlock events.
    • Regularly review execution plans and index usage.
    • Educate developers on safe transaction design patterns.

Result: By capturing deadlock graphs, analyzing query patterns, and applying fixes like consistent access order, indexing, and retry logic, you eliminate deadlocks or reduce their frequency, ensuring stable production performance.

Interview Summary:
“When I encounter a deadlock in production, I capture the deadlock graph using Extended Events, analyze which queries and resources are involved, and then fix it by enforcing consistent access order, optimizing indexes, shortening transactions, or enabling snapshot isolation. I also add retry logic in the application. This systematic approach ensures deadlocks are resolved and prevented in the future.”
