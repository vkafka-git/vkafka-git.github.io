Top 50 SQL Server & RDBMS Interview Questions

Curated for Tech Leads & Principal Developers (16+ Years Experience)

1. SQL Core Concepts & Architecture

Q1. What is the logical order of execution of a SQL query?
The logical order differs significantly from the syntactic order written by developers. Understanding this is critical for querying accuracy and optimization:
  1. FROM / JOIN (Data gathering across tables)
  2. WHERE (Row-level filtering)
  3. GROUP BY (Row grouping/aggregation setup)
  4. HAVING (Group-level filtering)
  5. SELECT (Column projection and Window function evaluation)
  6. DISTINCT (Deduplication of projected rows)
  7. ORDER BY (Final sorting)
  8. LIMIT / OFFSET / TOP (Row counts restriction)
Q2. Explain the difference between Clustered and Non-Clustered indexes.
  • Clustered Index: Dictates the physical storage layout of the table data rows. Because the table data itself can only be sorted in one way, there can only be one clustered index per table (typically aligned to the Primary Key). The leaf nodes contain the actual data rows.
  • Non-Clustered Index: A separate B-Tree architecture completely decoupled from the data rows. It contains structured index keys and pointers (either a Row ID or the Clustered Index Key) back to the actual data location. A table can sustain multiple non-clustered indexes.
Q3. What is a Composite Index, and what is the "Left-Prefix Rule"?
A composite index is an index constructed across multiple separate columns (e.g., Index(ColA, ColB, ColC)). The Left-Prefix Rule dictates that the query optimizer can only utilize the index if the query constraints include the leftmost column(s) specified in the index definition. A lookup filtering on (ColA) or (ColA, ColB) utilizes the structure efficiently; filtering solely on (ColB, ColC) or (ColC) completely invalidates it.
Q4. Explain the differences between WHERE and HAVING.
  • WHERE performs filtering on individual rows before group compositions or calculations occur. It cannot evaluate or parse aggregate expressions (e.g., SUM(), COUNT()).
  • HAVING executes filters exclusively on group records after the execution of the GROUP BY sequence. It evaluates conditions explicitly based on summary operations.

Q6. Explain UNION vs UNION ALL.
  • UNION combines distinct result outputs from multiple distinct query targets and executes an implicit distinct sort operation to eliminate duplicate rows, making it resource-heavy.
  • UNION ALL merges individual results concurrently without performing a sorting pass or removing duplicate rows, offering significantly faster throughput.
Q7. What is an Execution Plan, and how do you use it as a Tech Lead?
An execution plan is a physical breakdown mapping how the database query engine evaluates and returns results for a specific statement. It visually demonstrates index coverage, join loops, hashing operations, and implicit conversions. Tech Leads look for high-cost Table Scans, Key Lookups, and large differences between estimated and actual row counts to identify outdated statistics or structural index deficiencies.
Q8. What is the difference between an Index Scan and an Index Seek?
  • Index Scan: The database engine traverses the entire B-Tree structure from leaf to leaf, reading every row to capture matches. This occurs when search predicates are missing proper indexing columns.
  • Index Seek: The engine uses index criteria to pinpoint the exact memory/page boundaries of the target records directly. This is highly efficient.
Q9. What is Database Normalization, and what are 1NF, 2NF, and 3NF?
Normalization organizes transactional database schemas to mitigate data redundancy and improve structural data integrity:
  • 1NF: Ensures all table columns hold atomic, indivisible values, and rules out repetitive group configurations.
  • 2NF: Complies with 1NF and guarantees all non-key columns depend explicitly on the full Primary Key (eliminates partial key dependencies).
  • 3NF: Complies with 2NF and establishes that no non-key columns maintain dependency links to other non-key columns (eliminates transitive dependencies).
Q10. Explain the architectural trade-offs of Over-Normalization vs. Denormalization.
  • Normalization: Optimizes Write-intensive Systems (OLTP) by drastically reducing data footprints, ensuring data consistency, and minimizing maintenance locking. It increases complexity for read paths due to extensive multi-table joins.
  • Denormalization: Optimizes Read-intensive environments (OLAP/Reporting) by introducing controlled redundancies or pre-aggregating metrics. It eliminates compute overhead on joins, but slows down writes and introduces data anomaly risks.

2. Transactions, Concurrency & Isolation Levels

Q11. What are ACID properties in an RDBMS context?
  • Atomicity: Guarantees a unit of work commits entirely or rolls back completely ("All or nothing").
  • Consistency: Ensures transitions transform database states within strict compliance boundaries of all active schema constraints.
  • Isolation: Separates concurrent transaction modifications so states match serial execution order patterns.
  • Durability: Guarantees that committed records persist across hardware or OS failures.

Q13. What are Dirty Reads, Non-Repeatable Reads, and Phantom Reads?
  • Dirty Read: Tx1 accesses records currently altered by Tx2 before Tx2 issues a formal commit. If Tx2 aborts and rolls back, Tx1 handles phantom data.
  • Non-Repeatable Read: Tx1 fetches a row target; Tx2 executes an update or delete statement against that precise row and commits. Tx1 re-reads the data and finds discrepancies.
  • Phantom Read: Tx1 polls a range of matching criteria rows. Tx2 inserts an entirely new row matching that scope and commits. Tx1 re-reads the range and gets an extra record.
Q14. Explain Snapshot Isolation and Row Versioning (MVCC).
Multi-Version Concurrency Control (MVCC) leverages row versioning schemas to handle transaction isolation instead of acquiring heavy exclusive locks. When a transaction modifies a record, the engine creates and isolates historical snapshots of previous row states (e.g., inside tempdb for SQL Server). Readers fetch unchanged point-in-time states without blocking active writers, and writers execute without blocking readers.
Q15. What is a Deadlock, and how do you prevent and troubleshoot it?
A deadlock occurs when two or more active transactions maintain exclusive locks on individual resources while requesting lock access to structures held by the other, establishing an unresolvable cyclic block.
  • Prevention: Ensure database transactions acquire resources in a uniform, predictable table sequence across the application layer; avoid long-running, bulky units of work; lower isolation constraints where safe; leverage index design to bypass collisions.
  • Troubleshooting: Extract deadlock graphs, enable diagnostic flags (e.g., Trace Flag 1222 in SQL Server), or aggregate Extended Events trace records.
Q16. Compare Optimistic vs. Pessimistic Concurrency control paradigms.
  • Pessimistic: Locks database records immediately upon execution access, blocking competing statements until processing finishes. Designed for heavy data contention scenarios.
  • Optimistic: Processes mutations without taking row locks initially. Right before saving, it reviews a timestamp or version marker column. If the record changed, the transaction fails and throws a concurrency error for the application to handle. Designed for low data contention environments.
Q17. What are Intent Locks (IS, IX)?
Intent locks are structural lock abstractions captured at higher layers of the database hierarchy (such as table or page levels) right before low-level fine-grained row locks are taken. They signal down the chain that granular modifications exist below, preventing a competing query from acquiring global table locks that would disrupt minor row operations.

3. Window Functions & Advanced Querying

Q18. What is a Window Function, and how does it differ from a GROUP BY expression?
Window functions execute specialized aggregate calculations across an isolated subset of table records mapped to the current row context. Unlike GROUP BY, window functions do not collapse individual rows into a single summary output. Every individual record preserves its unique identity while retaining analytical context.
Q19. Explain the behavioral variances between ROW_NUMBER(), RANK(), and DENSE_RANK().
When parsing identical matching values (e.g., scores: 95, 95, 85):
  • ROW_NUMBER() outputs a strict incremental sequence regardless of ties: 1, 2, 3.
  • RANK() applies identical values to ties, but skips numbers for subsequent evaluations to match count footprints: 1, 1, 3.
  • DENSE_RANK() applies identical values to ties, but keeps continuous numeric rankings without skipping numbers: 1, 1, 2.
Q20. How do LEAD() and LAG() window functions work?
They enable a statement to pull data parameters from an alternative row in the active dataset without using a self-join:
  • LAG() reads specific attributes from a previous row step aligned to a configured offset.
  • LEAD() pulls data values from a trailing row step aligned to a configured offset.
Q21. What is the explicit role of the PARTITION BY clause?
PARTITION BY partitions the window function's target result layout into distinct subgroups. The analytical calculation restarts from scratch when crossing over partition boundaries, isolating calculations to specific logical groups.
Q22. What is a Common Table Expression (CTE), and when should you choose it over a Subquery or Temp Table?
A CTE represents an inline, isolated temporary result set scoped within the context of a single DML statement.
  • Use CTE: To improve query readability, structural modularization, or to handle recursive hierarchic records.
  • Use Temp Table: When processing highly volatile datasets that require iterative access across independent steps, or require their own unique indexes for high-volume joins.
Q23. How does a Recursive CTE process hierarchical records?
A recursive CTE references its own output structure. It evaluates an initial Anchor Member query (establishing base records), then links via UNION ALL to a Recursive Member query that references the parent CTE name. It loops until the relational step yields no matching rows.
Q24. Explain CROSS APPLY vs. OUTER APPLY (Lateral Joins).
Used to join a principal data record set to an inline table-valued function or correlated subquery evaluated row-by-row against the outer data elements:
  • CROSS APPLY models an INNER JOIN behavior; rows from the outer scope are excluded if the subquery returns an empty dataset.
  • OUTER APPLY models a LEFT OUTER JOIN behavior; outer rows are preserved, populating subquery columns with NULL if no records are matched.

4. Performance Tuning & Query Optimization

Q25. Walk through your step-by-step methodology for debugging a slow-running query.
  1. Review the actual query execution plan.
  2. Check for high-cost operations (e.g., Table/Index Scans, heavy Hash Matches instead of Nested Loops).
  3. Evaluate index coverage and look for warning markers or missing statistics warnings.
  4. Analyze precise operational runtime footprints via SET STATISTICS IO, TIME ON.
  5. Check for parameter sniffing issues or implicit data type conversions.
  6. Refactor problematic constructs (e.g., remove column-level expressions in the WHERE clause).
Q26. What is Parameter Sniffing, and how do you handle it?
Parameter Sniffing happens when the database optimizer compiles a specific execution plan optimized for the exact parameter values provided during the plan's initial compile run. If future requests invoke parameter inputs with significantly different data densities, the cached plan can run slowly.
Mitigation: Inject hints such as OPTIMIZE FOR UNKNOWN, RECOMPILE, or assign input parameters to local variables inside the stored procedure scope.
Q27. What does it mean when a query predicate is non-SARGable? Give an example.
A predicate condition is SARGable (Search Argumentable) if the query engine can directly leverage a B-Tree index to perform a direct seek. Using functions, arithmetic, or type casting on columns inside the WHERE clause renders it non-SARGable, forcing a full index/table scan.
Non-SARGable example: WHERE YEAR(OrderDate) = 2026
SARGable alternative: WHERE OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01'
Q28. Compare the three physical join operators: Nested Loops, Hash Match, and Merge Join.
  • Nested Loops: Highly efficient for small outer data tables joined to properly indexed inner tables. Loops through outer rows and performs a quick lookup into the inner structure.
  • Merge Join: Fast and lightweight; occurs when both inputs are pre-sorted along the join key attributes. It processes both inputs simultaneously.
  • Hash Match: Resource-heavy join path used for unindexed, large data inputs. It constructs an in-memory hash table of the smaller dataset to probe matching values from the larger dataset, using more memory.
Q29. What are Covering Indexes, and how do INCLUDE columns help?
A covering index houses all column elements requested by a query (covering SELECT, WHERE, and JOIN requirements). This allows the database engine to return data completely from the index leaf nodes without performing a secondary lookup into the base table pages. Adding columns via INCLUDE attaches non-key data fields strictly to the leaf level, providing a covering path without increasing the sorting or maintenance overhead of the main index key structure.
Q30. How do you identify and handle Index Fragmentation?
Fragmentation occurs as continuous modifications alter database rows, causing data pages to split and drop out of clean physical order.
  • Handling: If fragmentation levels reside between 5% and 30%, run an online index Reorganize operation. If fragmentation exceeds 30%, perform an index Rebuild to restructure the physical layout.
Q31. What are Database Statistics, and why are they critical?
Database statistics store distribution and density maps of values across columns and indexes. The query optimizer relies on this metadata to estimate cardinality (row counts per operation step) and select execution plans. Corrupt or outdated statistics can lead to sub-optimal plan generation and slow queries.

5. Programmability, Architecture & Security

Q32. Contrast Stored Procedures against User-Defined Functions (UDFs).
  • Stored Procedures: Can return multiple outputs, perform full DML mutations, manage transactions (e.g., COMMIT / ROLLBACK), and output execution status codes. They can optimize execution paths efficiently.
  • UDFs: Must compute and return a singular value or explicit table structure. They cannot execute side-effecting DML operations, cannot manage transactions, and can be embedded inside a SELECT projection. Scalar UDFs can sometimes introduce performance overhead if executed row-by-row.
Q33. What is a View, and what is an Indexed/Materialized View?
  • View: A virtual reference structure representing a saved query definition. It consumes no physical storage.
  • Indexed / Materialized View: A view that has been structurally finalized with a physical clustered index. The database engine calculates and stores the view's data on disk, automatically updating it when base tables shift. This is ideal for optimizing complex aggregation queries over large tables.
Q34. What are Triggers? Distinguish between AFTER and INSTEAD OF triggers.
Triggers represent automated processing units invoked in response to explicit data mutation paths (INSERT, UPDATE, DELETE):
  • AFTER Trigger: Fires after the underlying DML execution completes successfully and passes all integrity checks.
  • INSTEAD OF Trigger: Executes in place of the triggering DML statement, intercepting the operation. This is useful for translating modifications targeting complex views.
Q35. Explain the purpose of the INSERTED and DELETED tables in triggers.
These represent temporary, system-managed memory tables populated during DML execution loops:
  • INSERTED: Preserves state captures of newly added or updated rows during INSERT and UPDATE sequences.
  • DELETED: Preserves state captures of rows removed or replaced during DELETE and UPDATE sequences.
Q36. What is SQL Injection, and how do you protect database ecosystems against it?
SQL Injection is a vulnerability where unvalidated user inputs are concatenated directly into execution strings, allowing malicious commands to execute inside the database engine.
Defenses: Enforce parameterized inputs / prepared statements, apply strongly typed variable definitions, avoid dynamic execution paths unless using parameterized bindings, and implement the Principle of Least Privilege across data connections.

6. Advanced Architecture & Modern Design Patterns

Q37. Explain Database Sharding vs. Horizontal Table Partitioning.
  • Horizontal Table Partitioning: Divides a single massive table structure inside a single database instance into separate row groups based on a partition key (e.g., partitioning an orders table by year).
  • Sharding: A architecture where data subsets are spread across multiple independent database instances/servers, physically isolating compute and storage profiles to scale horizontal growth.
Q38. What is Replication, and what are its main architectural forms?
Replication clones and streams database records across independent endpoints to support read-scale operations or high availability:
  • Snapshot Replication: Overwrites downstream targets periodically with a point-in-time capture of the source schema.
  • Transactional Replication: Streams incremental DML data modifications in near real-time from source to target servers.
  • Merge Replication: Allows distributed targets to execute independent mutations, then aggregates changes later using conflict-resolution rules.
Q39. What is a Cursor, and why is it generally discouraged in high-concurrency systems?
A cursor is an element that traverses a query result set row-by-row. Cursors run counter to relational query engines, which are designed for optimized **set-based** operations. Cursors introduce row-by-row lock contention and higher memory consumption, which can impact performance in high-concurrency systems.
Q40. Explain the implications of using a GUID/UUID as a Primary Key compared to an Auto-Incrementing Integer.
  • Auto-Incrementing Integer (Int/BigInt): Compact storage footprint (4–8 bytes). Sequential growth helps prevent page splitting during inserts, but sequential numbers can reveal business scale or create insertion bottlenecks in highly distributed engines.
  • GUID / UUID: Larger storage footprint (16 bytes). Guarantees global identity generation uniqueness across distributed systems, but random UUID patterns can cause severe index fragmentation and page splits when applied as a Clustered Key.
Q41. What is Columnstore Indexing, and when should you adopt it?
Columnstore indexes compress and organize table storage data along columns rather than traditional rows. They offer high data compression ratios and query speeds for analytical processing over massive datasets (millions of rows), making them well-suited for data warehousing workloads.

Q43. Write a query to delete all duplicate rows from a table named Users based on Email, keeping the row with the lowest Id.
WITH CTE_Duplicates AS (
    SELECT Id, Email,
           ROW_NUMBER() OVER (PARTITION BY Email ORDER BY Id ASC) as RowNum
    FROM Users
)
DELETE FROM CTE_Duplicates 
WHERE RowNum > 1;
Q44. Given a table Logins with columns UserId and LoginDate, write a query to find users who logged in on consecutive days.
WITH CTE_Lag AS (
    SELECT UserId, LoginDate,
           LAG(LoginDate) OVER (PARTITION BY UserId ORDER BY LoginDate) as PrevLoginDate
    FROM Logins
)
SELECT DISTINCT UserId 
FROM CTE_Lag 
WHERE DATEDIFF(day, PrevLoginDate, LoginDate) = 1;

Q47. Write a query to retrieve the top 3 highest-paid employees inside each department.

    SELECT Name, DepartmentId, Salary,
           DENSE_RANK() OVER (PARTITION BY DepartmentId ORDER BY Salary DESC) as SalaryRank
    FROM Employees

Q48. Given a Sales table with columns SaleDate and Amount, write a query to compute a running total of the sales sorted by date.
SELECT SaleDate, Amount,
       SUM(Amount) OVER (ORDER BY SaleDate ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS RunningTotal
FROM Sales;

SELECT Id + 1 
FROM Orders o
WHERE NOT EXISTS (
    SELECT 1 FROM Orders i WHERE i.Id = o.Id + 1
) AND Id < (SELECT MAX(Id) FROM Orders);
Q50. Write a scenario query checking for a correlation between an Employee's salary and their Department's average salary.
SELECT e.Name, e.DepartmentId, e.Salary, d.AvgSalary
FROM Employees e
INNER JOIN (
    SELECT DepartmentId, AVG(Salary) as AvgSalary
    FROM Employees
    GROUP BY DepartmentId
) d ON e.DepartmentId = d.DepartmentId
WHERE e.Salary > d.AvgSalary;

6. Distributed Systems & Cloud Architecture

Q51. How do you implement the "Outbox Pattern" to guarantee reliable messaging between SQL Server and a message broker (like Kafka or RabbitMQ)?
To prevent dual-write failures (where a database commit succeeds but the subsequent message broker publish fails), the Transactional Outbox Pattern is used. Inside a single local ACID transaction, the application updates the core business entity table and inserts an event payload into a dedicated Outbox table. A separate, asynchronous background polling service or an engine parsing the database transaction log (CDC) reads unread rows from the Outbox table, publishes them to the message broker, and marks them as processed upon acknowledgment. This shifts the architectural boundary from a fragile distributed transaction to reliable eventual consistency.
Q52. Explain the difference between "Read-After-Write Consistency" and "Eventual Consistency" in distributed read-replica configurations.
  • Read-After-Write Consistency: Guarantees that if a user submits a data modification, their immediate subsequent read request will accurately display that modification. Architecturally, this requires routing write-dependent read operations explicitly to the Primary node.
  • Eventual Consistency: Occurs when read traffic is offloaded to asynchronous Read Replicas (e.g., Always On replicas utilizing asynchronous commit). Due to inherent replication lag, a user might write data to the primary node but temporarily fetch a stale data state from the replica until the transaction log catch-up loop completes.
Q53. How do you design a database schema to support a "Global Multi-Region" architecture where data must be written locally in different countries?
  1. Primary Key Strategy: Avoid auto-incrementing integer identities to eliminate multi-region value collisions; use Sequential GUIDs (via NEWSEQUENTIALID()) to maintain uniqueness while reducing index B-Tree fragmentation.
  2. Data Partitioning: Embed a RegionId or CountryCode directly into a composite primary/clustering key layout.
  3. Conflict Resolution Schema: Include high-precision synchronization timestamps to support Last-Write-Wins or structural state tracking for CRDTs (Conflict-free Replicated Data Types) if designing active-active replication models.
Q54. Explain the "Saga Pattern" and how database locks are handled compared to a traditional 2-Phase Commit (2PC).
  • 2-Phase Commit (2PC): Coordinates a distributed transaction across multiple database nodes by holding global locks across all participating nodes concurrently until everyone agrees to commit. This introduces severe latency and single-point-of-failure vulnerabilities.
  • Saga Pattern: Deconstructs a distributed transaction into a sequence of distinct, localized database transactions. Each independent microservice executes its local unit of work, releases its local database locks immediately, and publishes a trigger event. If a downstream service fails, the orchestration layer invokes explicit Compensating Transactions to run reverse operations (e.g., executing an account refund to roll back a charge).
Q55. What is "Database Polyglot Persistence," and how do you evaluate when to move data out of SQL Server?
Polyglot persistence is the practice of using diverse database technologies tailored for specific data access patterns within an enterprise ecosystem. You should architecturally offload data from SQL Server under these conditions:
  • Unstructured Blobs/Media Logs: Move to Cloud Object Storage (e.g., Azure Blob, AWS S3) to prevent heavy LOB data from polluting the SQL Server memory buffer pool.
  • High-Velocity, Transient Volatile Data: Move session states and caching components to in-memory key-value stores like Redis.
  • Complex Deeply Connected Networks: Move highly interconnected relationship models to dedicated graph databases like Neo4j.

7. Extreme Performance Tuning & Internals

Q56. What is "Latch Contention" (PAGIOLATCH vs PAGELATCH), and how do you diagnose it?
Latches are internal, lightweight synchronization mechanisms used by the engine to protect memory structures.
  • PAGIOLATCH waits indicate that a query thread is blocked waiting to read a data page from slow physical disk storage into the memory buffer pool. This points to I/O constraints or missing index coverage forcing table scans.
  • PAGELATCH waits indicate concurrency contention for a data page that already resides in memory. This typically occurs on high-throughput write systems using sequential IDENTITY values, where multiple concurrent threads collide trying to write to the exact same trailing leaf-node page.
Q57. What are "Implicit Conversions," and why are they silent killers of production performance?
An implicit conversion occurs when a query passes a search predicate data type that does not precisely match the target column's schema configuration (for instance, passing an NVARCHAR argument against a VARCHAR column). To evaluate the condition, SQL Server must apply a scalar type-conversion function to every single row of the underlying column inside the execution loop. This renders the query completely non-SARGable, turning an efficient Index Seek into an expensive, CPU-intensive Index Scan.
Q58. Explain the difference between MAXDOP and "Cost Threshold for Parallelism."
  • MAXDOP (Maximum Degree of Parallelism) dictates the maximum number of CPU cores/threads assigned to evaluate a single parallel query execution plan branch.
  • Cost Threshold for Parallelism: The engine's internal optimizer cost calculation limit at which SQL Server determines a query is expensive enough to warrant splitting it across multiple parallel CPU paths. The default value of 5 is heavily outdated; leads elevate this baseline to 50+ to prevent minor operational queries from misusing parallel resources.
Q59. What is "Spinlock Contention" in SQL Server internals?
Spinlocks are highly granular, short-lived mutual exclusion primitives used by the engine to regulate access to core internal memory allocations (like the buffer pool hash buckets). Unlike standard locks, a thread waiting on a spinlock does not yield or enter a sleep state; it continuously loops ("spins") on the CPU core testing for availability. High spinlock wait metrics point to deep internal concurrency bottlenecks operating under intense CPU workloads.
Q60. How do "Filtered Indexes" save space and speed up queries? Give an architecture example.
A filtered index builds an optimized B-Tree structure over a targeted subset of table records by introducing a WHERE condition directly into the index generation syntax. 
CREATE NONCLUSTERED INDEX IX_Orders_Unprocessed
ON Orders(OrderDate)
WHERE Status = 'Pending';
Instead of tracking 200 million rows, the index only tracks the minor fraction of records that active asynchronous background processors require. This maximizes memory cache density, shrinks disk footprints, and reduces index maintenance overhead.

8. Security, Compliance & Governance

Q61. How do you design Data Masking vs. Column-Level Encryption for compliance (e.g., GDPR, PCI-DSS)?
  • Dynamic Data Masking (DDM): Obfuscates sensitive data on the fly at the presentation layer (e.g., displaying credit cards as XXXX-XXXX-XXXX-1234) based on the database user's execution privilege. The raw data remains completely unencrypted on disk and in memory buffers.
  • Column-Level Encryption: Uses cryptographic keys to structurally transform row values before storage. It physically encrypts the data layout, limits index-driven search performance (disallowing smooth range scans), and imposes a notable CPU cost for ongoing encryption/decryption cycles.
Q62. Explain the vulnerability of "SQL Injection in Stored Procedures" if EXEC() or sp_executesql is misused.
Encapsulating code inside a stored procedure does not automatically guarantee security. If untrusted user text variables are directly concatenated into a dynamic SQL string execution block within the procedure body, it remains vulnerable to injection: 
-- HIGHLY VULNERABLE SP PATTERN
SET @SqlString = 'SELECT * FROM Users WHERE Name = ''' + @InputParam + '''';
EXEC(@SqlString);
To eliminate this flaw, always pass dynamic SQL queries through sp_executesql and enforce explicit, strongly-typed parameter binding definitions.
Q63. What is an "Infrastructure Audit Trail," and how do you monitor unauthorized Schema Changes (DDL)?
To establish an immutable governance ledger against unauthorized structural variations, implement database or server-level DDL Triggers. These elements intercept modification actions (such as DROP_TABLE, ALTER_INDEX), extract execution context data via EVENTDATA() (including machine footprint, user logins, and the raw SQL text), log the parameters to a hardened audit table, and can automatically execute a ROLLBACK if safety compliance boundaries are violated.

9. Database Programmability & Advanced Patterns

Q64. Explain the performance risk of using Scalar User-Defined Functions (UDFs) and how SQL Server 2019+ mitigates it.
Historically, scalar UDFs forced SQL Server to adopt an iterative row-by-row processing loop known as "RBAR" (Row-By-Agonizing-Row). The optimizer could not calculate cost estimations on these paths, disabling parallel processing and significantly degrading query execution speed. SQL Server 2019 introduced Scalar UDF Inlining, which automatically transforms eligible scalar function routines into equivalent relational subqueries behind the scenes, allowing the engine to leverage set-based execution plans and indexes.
Q65. What are "In-Memory OLTP" (Hekaton) tables, and when should they be integrated?
In-Memory OLTP tables utilize memory-optimized data layouts that decouple storage paths completely from traditional disk pages, using a lock-free concurrency architecture driven by optimistic row versioning. They should be integrated into high-concurrency environments experiencing extreme ingestion pressures (such as IoT telematics processing), heavy session-state tracking modules, or systems suffering from intense tempdb allocation bottlenecks. They compile directly into native C DLLs for execution.
Q66. How do you handle "Concurrency Checks" using a rowversion / timestamp column in .NET applications?
To protect against lost updates under optimistic concurrency models, add an automatically updating rowversion binary column to the table schema. The .NET application reads this tracking value and passes it back during mutation requests: 
UPDATE Products 
SET Stock = @NewStock 
WHERE Id = @ProductId AND CurrentRowVersion = @ExpectedRowVersion;
If a competing thread altered the row state in the interval between read and write, the underlying row version shifts, the statement updates zero rows, and Entity Framework or ADO.NET throws a concurrency exception to trigger retry or resolution loops.
Q67. Explain the "Entity-Attribute-Value (EAV)" anti-pattern, its performance limitations, and modern alternatives.
The EAV anti-pattern attempts to support dynamic schemas by breaking entities down into generic rows structured as [EntityId, AttributeName, AttributeValue]. While highly flexible, fetching a complete object profile requires executing repetitive self-joins for every attribute evaluated, severely impacting performance and breaking type safety. The modern alternative is a relational-hybrid architecture, keeping core static attributes structured in standard columns while offloading dynamic fields into a native JSON column paired with filtered indexes or JSON_VALUE computed columns.

10. Data Lifecycle Management & Maintenance

Q68. What is the "Sliding Window" pattern in table partitioning?
The Sliding Window pattern is an automated maintenance routine for time-series architectures. A scheduled database job rolls partition bounds forward over time by executing three sequential metadata steps:
  1. Empties the oldest historical partition range by swapping its boundaries into an isolated historical archive table using the near-instantaneous ALTER TABLE ... SWITCH statement.
  2. Executes a MERGE operation on the old partition function boundary.
  3. Executes a SPLIT operation on the newest boundary range to prepare storage blocks for incoming future data streams.
This strategy keeps active operational tables at a stable, high-performance physical volume size.
Q69. How do you rebuild massive indexes online without knocking out a high-availability production cluster?
Execute the index rebuild using the ONLINE = ON hint to ensure concurrent transactional workloads retain full read/write access to the active pages during construction. Furthermore, append the RESUMABLE = ON flag (available in SQL Server 2017+). This allows you to pause a heavy index rebuild operation during peak operational traffic windows to preserve system resources and resume execution later from the exact page boundary it left off without discarding completed work.
Q70. Explain "Mirrored Backups" and "Checksum Verification" for enterprise disaster recovery.
  • Backup Checksum: Enforces page integrity validation routines during the backup generation stream. If any database page contains underlying silent corruption on disk, the backup operation halts and alerts early, preventing the system from backing up a corrupted image.
  • Mirrored Backups: Instructs the storage engine to split and write identical byte streams to multiple distinct physical target locations simultaneously (such as a fast local array and a secure remote network storage location), eliminating post-backup file copying stages.

11. Real-World Scenario Engineering

Q71. Production Incident: CPU spikes to 100%, and query blockings skyrocket. What are your first 3 commands?
  1. Execute sp_whoisactive (or query sys.dm_exec_requests coupled with sys.dm_exec_sql_text) to pinpoint the active connection IDs executing the longest-running statements, sorted by CPU utilization or open transaction locks.
  2. Review top global wait statistics to categorize the structural bottleneck: 
    SELECT wait_type, waiting_tasks_count, wait_time_ms 
FROM sys.dm_os_wait_stats 
ORDER BY wait_time_ms DESC;
  3. Query the locking hierarchy via sys.dm_tran_locks and cross-reference with session block maps to isolate the root blocker ID holding exclusive resources.
Q72. Scenario: Your .NET API throws a "Timeout Expired" exception, but the query runs in under 1 second when pasted into SSMS. Why?
This behavior is typically driven by Parameter Sniffing acting across divergent SET environments. SSMS connections run with specific environment settings (such as ARITHABORT ON), whereas .NET connections pass through ADO.NET with alternative defaults. Because SQL Server treats differing connection environmental configurations as separate execution profiles, it caches separate plans. The plan cached for the .NET profile is likely optimized for an unrepresentative parameter density and timing out, while your SSMS session triggers or compiles a fresh, efficient plan layout.
Q73. Scenario: A legacy financial system requires calculating a rolling 30-day average cash balance over millions of records. How do you implement this efficiently?
Avoid row-by-row cursors or subqueries. Establish a covering index structured on the transaction tracking date and account identifier columns, then execute a set-based query leveraging window aggregation boundaries: 
SELECT AccountId, TransactionDate, Balance,
       AVG(Balance) OVER(
           PARTITION BY AccountId 
           ORDER BY TransactionDate 
           ROWS BETWEEN 29 PRECEDING AND CURRENT ROW
       ) AS Rolling30DayAverage
FROM CashLedger;
Q74. Scenario: You must migrate a 500GB table to a new schema format with near-zero downtime. What is your strategy?
  1. Deploy the new target table containing the updated structural schema parameters.
  2. Implement an Instead-Of Trigger or an application-layer dual-write path so that all incoming production INSERT, UPDATE, and DELETE statements modify both tables simultaneously.
  3. Execute a background chunking script to migrate historical records from the old layout to the new table in small batches (e.g., 5,000 records per transaction block bound by primary key scopes) to prevent log escalation.
  4. Once the historical copy captures up to the dual-write threshold, run a quick metadata operation to rename the tables and drop the legacy table.
Q75. Scenario: A reporting query needs to join a table variables output to a 10M row table, resulting in very slow performance. How do you optimize it?
The query optimizer assumes a table variable holds exactly 1 row because table variables lack distribution statistics. When joining this 1-row estimate against a 10 million row table, the optimizer selects an inefficient Nested Loops join plan. To optimize this path, attach the hint OPTION (RECOMPILE) at the base of the statement, forcing the engine to review the actual runtime row footprint of the variable during compilation. This guides the engine to choose a much more efficient Hash Match or Merge join plan. Alternatively, refactor the variable into a standard temporary table (#temp).

🟢 Foundational Concepts

Q1. Explain the differences and physical rules between a Primary Key, Unique Key, and Foreign Key.
  • Primary Key (PK): Uniquely identifies each record in a table. It strictly prohibits NULL values and automatically establishes a Clustered Index on the target column(s) by default. There can only be exactly one PK per table.
  • Unique Key (UK): Enforces uniqueness constraints across non-primary columns. Unlike a PK, a Unique Key allows a single NULL value (in SQL Server context; other RDBMS engines allow multiple NULLs). It constructs a Non-Clustered Index by default, and tables sustain multiple Unique Keys.
  • Foreign Key (FK): Defines a referential integrity relationship mapping a child table column to a parent table PK or UK column. It prevents orphan records. It does not index columns automatically; leads must index FK columns manually to bypass lock cascades and slow join lookups.
Q2. Deep Dive: Explain INNER JOIN, LEFT JOIN, RIGHT JOIN, and FULL JOIN behaviors.
  • INNER JOIN: Evaluates and extracts intersecting matching rows from both tables matching the explicit join predicate. Unmatched rows are omitted.
  • LEFT (OUTER) JOIN: Returns all records residing in the left table, along with matching rows found in the right table. If no predicate match occurs, the right-side properties populate as NULL.
  • RIGHT (OUTER) JOIN: Reverses Left Join logic, preserving all records from the right table and appending matches from the left. (Tech Leads prefer converting these to LEFT JOIN for unified visual flow).
  • FULL (OUTER) JOIN: Combines Left and Right join mechanics. It retains all records from both entities, outputting NULL parameters wherever a conditional match is completely missing on either side.
Q3. Write a standard SQL query to identify duplicate records in a table based on specific columns.
To isolate duplicate entries across specific attributes (e.g., Email and CompanyId), leverage the GROUP BY clause alongside a HAVING COUNT(*) > 1 constraint: 
SELECT Email, CompanyId, COUNT(*) as OccurrenceCount
FROM Users
GROUP BY Email, CompanyId
HAVING COUNT(*) > 1;
Q4. Explain the interaction rules between GROUP BY and aggregate functions.
Aggregate functions (like SUM(), AVG(), COUNT()) compress raw row datasets down into individual calculated summary fields. The GROUP BY clause establishes the logical boundaries for these calculations. A strict syntax rule applies: any non-aggregated column projected within the SELECT block must be explicitly declared inside the GROUP BY expression.
Q5. Compare CHAR vs. VARCHAR from a physical storage perspective.
  • CHAR(N): Allocates static, fixed-length physical disk storage bytes equal to N. If the string data is smaller than N, the engine space-pads the remaining boundaries. Ideal for unchanging structural strings (e.g., Currency codes like 'USD', Status keys like 'ACT') to avoid variable-length tracking overhead.
  • VARCHAR(N): Allocates variable-length physical storage scaling down to the actual characters written, adding a 2-byte structural prefix tracking the length parameter. It saves storage footprints on volatile fields (e.g., Names, Emails) but can introduce row migration overhead if updates heavily expand the data footprint later.
Q6. Explain NULL handling logic and the implications of Three-Valued Logic in relational querying.
SQL implements Three-Valued Logic: conditions can evaluate to TRUE, FALSE, or UNKNOWN. A NULL represents an unassigned marker denoting the missing absence of data, rather than a value. Consequently, direct evaluations (e.g., Column = NULL) fail, outputting UNKNOWN. Developers must use explicit unary operators: IS NULL or IS NOT NULL.

🟡 Intermediate Performance & Real-World

Q7. What is a Covering Index, and how does it optimize high-throughput queries?
A covering index is a non-clustered index containing all data columns requested by a targeted query execution path (satisfying SELECT, WHERE, and JOIN operations). By appending non-key payload elements using the INCLUDE clause, the engine can fetch all required parameters directly from the leaf nodes of the B-Tree index, bypassing the need for an expensive secondary Key Lookup into the underlying table pages.
Q8. Write a query using standard window functions to fetch the Nth highest salary from an Employees table.
Using DENSE_RANK() is the most robust strategy because it properly handles duplicate salary inputs without skipping ranks: 
WITH RankedSalaries AS (
    SELECT Salary,
           DENSE_RANK() OVER (ORDER BY Salary DESC) as RankOrder
    FROM Employees
)
SELECT DISTINCT Salary 
FROM RankedSalaries 
WHERE RankOrder = @N;
Q9. Explain Horizontal Table Partitioning in SQL Server and its core optimization mechanics.
Table Partitioning maps a single large table object across independent physical storage allocations (Filegroups) bound to a designated column value (the Partition Key, such as TransactionDate). It utilizes a Partition Function to establish range thresholds and a Partition Scheme to map boundaries to storage. This setup accelerates execution via Partition Elimination (the query engine skips unneeded storage chunks completely) and permits fast index archives using ALTER TABLE ... SWITCH steps.
Q10. Contrast OLTP and OLAP schema design choices from an architectural perspective.
  • OLTP (Online Transaction Processing): Designed for highly transactional, concurrent read/write patterns. Uses normalized schemas (typically 3NF) to reduce data duplication, protect data integrity, and ensure thin, fast update transactions.
  • OLAP (Online Analytical Processing): Designed for heavy, complex reporting aggregation queries. Uses denormalized schemas (like **Star or Snowflake** layouts) with centralized Fact tables surrounded by wide, flattened Dimension tables to reduce join overhead and optimize scan rates.
Q11. How do you implement robust, high-performance audit logging inside SQL Server?
  • SQL Server Audit: A native feature driven by Extended Events architecture. It captures granular database or server actions (e.g., tracing ad-hoc table SELECT paths), writing logs asynchronously to secure binary files or OS Event logs.
  • Temporal Tables: System-versioned tables that automatically maintain a history table shadow track. Modifying or removing rows triggers the engine to transparently write old historical profiles into the history table alongside validity time ranges, allowing point-in-time state checks via FOR SYSTEM_TIME AS OF statements.

🔴 Advanced Architectural & Problem-Solving

Q12. How would you design a database schema for a high-concurrency ride-sharing application like Uber at massive scale?
Isolate rapidly changing telemetry updates from highly transactional lookup tables. Store static core records (Users, Drivers, Vehicles, Rides) within normalized tables using spatial indices on the GEOGRAPHY data type to optimize localized matching routines via distance functions (e.g., .STDistance()). To scale hyper-frequent driver GPS updates, route transient coordinates away from the primary ACID RDBMS. Instead, stream location data to high-speed in-memory key-value databases (such as Redis Geospatial) and commit data back to SQL Server only when critical ride states transition (e.g., Requested, Completed).
Q13. What architectural strategies do you apply to ensure query stability over an Orders table containing 200M+ rows?
Implement horizontal range partitioning across a date boundary (e.g., monthly). Align all non-clustered indices to the partitioning scheme to ensure partition-isolated index maintenance tasks can run concurrently without locking global datasets. Apply PAGE data compression to reduce memory buffer pool consumption and decrease read I/O pressure. Finally, use partition switching routines to move historical data blocks into cold archive storage schemas.
Q14. Explain the operational and design differences between Fact and Dimension tables in data warehousing.
  • Fact Tables: Represent central transaction event data points. They store quantitative metrics (e.g., Revenue, Quantity) along with foreign keys linking out to surrounding dimension data. They are structurally narrow, vertical tables holding millions of rows.
  • Dimension Tables: Hold the descriptive context, attributes, and textual filters surrounding a business process (e.g., CustomerName, ProductCategory, StoreLocation). They are structurally wide, denormalized tables optimized for reporting lookup paths.
Q15. Compare the physical storage mechanics and lookups of Heap Tables against Clustered Tables.
  • Heap Table: Lacks a designated clustered index. Rows are placed without physical sorting order constraints into raw data pages. Finding records requires running a full table scan or referencing a non-clustered index that points directly to a physical Row Identifier (RID: file, page, slot number).
  • Clustered Table: Data rows are physically ordered and stored sorted along the criteria mapping the Clustered Index Key. Non-clustered index records point directly to the Clustered Key value instead of physical addresses, keeping lookups stable even when data pages split or reorganize.
Q16. How do you implement soft deletes at scale, and what are the performance pitfalls and solutions?
Soft deletes introduce an indicator flag column (e.g., IsDeleted BIT) to mark logical row removal without executing a destructive physical delete command.
Pitfalls: Queries must constantly append WHERE IsDeleted = 0 predicates, which can compromise the effectiveness of traditional composite indexes and complicate unique constraints.
Solution: Build a Filtered Index explicitly covering active items: 
CREATE UNIQUE NONCLUSTERED INDEX UX_Users_ActiveEmail
ON Users(Email)
WHERE IsDeleted = 0;
Abstract the filtering abstraction away from application code layers by wrapping tables inside database Views integrated with INSTEAD OF DELETE triggers to process the logic transparently.
Q17. Explain Change Data Capture (CDC) mechanics and its architectural use cases.
CDC asynchronously reads and parses the database transaction log to track all DML mutations (INSERT, UPDATE, DELETE) executed against targeted tables. A log-scraping engine extracts these transactions and populates system tracking tables with row states without introducing locking overhead or performance degradation to active application writes. It is highly effective for driving real-time ETL pipelines, feeding event streams (e.g., Kafka via Debezium), and maintaining external search clusters (e.g., Elasticsearch).
Q18. Contrast Database Replication against Log Shipping configurations for business continuity.
  • Transactional Replication: Operates at the individual database object level (tables, views). A distribution agent reads changes from the primary transaction log and replays those standalone DML commands onto a secondary subscriber database. The secondary target remains fully online and accessible for read-heavy offloading workloads.
  • Log Shipping: Operates at the global file backup tier. Automated jobs generate scheduled transaction log backup files at the primary node, transfer them across the network, and restore them sequentially onto a standby instance. The secondary node is offline or restricted to read-only connectivity during restoration loops.
Q19. How do you ensure reliable data consistency across independent microservices databases without using 2-Phase Commit (2PC)?
Avoid distributed 2-Phase Commits because their blocking locking protocols degrade system availability. Instead, leverage the Saga Pattern alongside the **Transactional Outbox Pattern**. The Saga orchestration splits distributed steps into local database transactions that release local locks immediately. If a downstream stage fails, compensating transactions are triggered to execute reverse actions. The Outbox pattern ensures that database mutations and outbound event logs are saved together atomically within a single local database transaction before broadcasting to a message broker.
Q20. Explain the CQRS (Command Query Responsibility Segregation) pattern at the database tier.
CQRS segregates the database mutation path (Commands: updates, deletes, inserts) from the data retrieval path (Queries: read paths). The write database is highly normalized to minimize transaction locking footprints and ensure strict data entry validation rules. The read database uses a denormalized layout (or a read-optimized storage engine) designed for rapid querying performance. Data synchronizes asynchronously from the write path to the read path via transaction log scraping or event pub/sub lines, accepting eventual consistency to optimize read and write scaling.
Q21. What are the multi-tenant database design architectures for SaaS environments, and how do you evaluate them?
  1. Database Per Tenant (Isolated): Separate physical instances for each customer. Delivers strong isolation and simplifies custom backups, but incurs high infrastructure overhead and maintenance complexity.
  2. Shared Database, Separate Schemas: Shared database container but tenants occupy segregated logical schemas (e.g., TenantA.Orders). Offers a balance of resource sharing and database separation.
  3. Shared Database, Shared Schema (Colocated): All tenants reside in the same data tables, isolated logically by a grouping attribute (e.g., TenantId). Provides maximum tenant density and low hosting costs, but requires strict enforcement (such as **Row-Level Security**) to prevent cross-tenant data leaks.
Q22. Compare Horizontal Scaling vs. Vertical Scaling database modern capabilities.
  • Vertical Scaling (Scale-Up): Adding more hardware capabilities (CPU cores, RAM capacity, NVMe storage IOPS) to a single existing database host. It requires zero application refactoring, but is constrained by physical hardware cost curves and keeps a single point of failure (SPOF).
  • Horizontal Scaling (Scale-Out): Spreading workloads across multiple independent compute endpoints by utilizing read-replicas, read/write nodes, or sharding managers. It supports virtually limitless scalability, but introduces architectural complexity regarding network routing and distributed data synchronization.
Q23. How do you secure sensitive data (PII) at rest and in use within SQL Server to meet compliance standards?
  • Transparent Data Encryption (TDE): Protects data at rest by encrypting the physical database pages, log structures, and system backup files on disk. The engine decrypts data transparently as it loads into server memory, protecting against physical storage theft.
  • Always Encrypted: Protects data in transit and in use. Cryptographic keys stay on the client driver side. Column encryption occurs prior to transmitting data over the network, ensuring sensitive attributes remain encrypted within the database memory buffer pool, protecting against compromised administrative users.
Q24. Explain Row-Level Security (RLS) architecture and its underlying execution flow.
Row-Level Security enforces data visibility constraints on data rows based on the execution attributes of the querying user session. It relies on an inline table-valued function containing security predicate validations (e.g., WHERE SalesRegion = SESSION_USER). This logic is bound to the target table via a **Security Policy**. The engine transparently inserts this predicate filter directly into incoming queries, preventing data leaks across security boundaries.
Q25. Contrast High Availability (HA) against Disaster Recovery (DR) enterprise options inside SQL Server.
  • Always On Availability Groups (HA Focus): Provides database-level redundancy across local server cluster infrastructure. By using Synchronous Commit data streaming, it guarantees zero data loss (RPO = 0) and triggers automatic connection string failovers if the primary server host experiences an outage.
  • Distributed Availability Groups (DR Focus): Connects distinct, independent availability groups across separate geographical data centers. It utilizes Asynchronous Commit to avoid injecting network latency into active application transactions, ensuring a warm standby destination is ready if an entire region goes offline.
Q26. What are the optimization and execution differences between Temp Tables and Table Variables?
  • Temp Tables (#TempTable): Instantiated within tempdb storage. They look and act like standard tables, maintaining full column distribution statistics, supporting custom index creation, and participating in transaction rollbacks. Best for large data operations (thousands of rows) requiring complex joins.
  • Table Variables (@TableVariable): Exist inside memory configurations but can spill to tempdb. They lack column statistics, leading the optimizer to assume a baseline cardinality of exactly 1 row (which can cause poor execution plans on large datasets). They do not participate in transactional rollbacks, making them ideal for short-lived lookup buffers.
Q27. How do you design and execute a large-scale batch insert operation efficiently to prevent system resource starvation?
Avoid running long, monolithic row-by-row transactions that can overflow the transaction log and cause lock escalation. Use bulk copy mechanisms (such as the SqlBulkCopy utility) configured for Minimal Logging to stream data pages directly to storage. If executing standard DML statements, process the data in controlled batches (e.g., 5,000 to 10,000 rows per loop cycle) and drop or disable non-clustered indexes prior to execution, rebuilding them once the data load concludes.
Q28. What are Query Hints, and what is your philosophy as a Tech Lead regarding their use?
Query hints (such as FORCESEEK, NOLOCK, OPTIMIZE FOR) override the query optimizer's default execution plan decisions. As a Tech Lead, my philosophy is that query hints should be treated as a **last resort**. Forcing specific join patterns or index use can lead to performance degradation over time as data distributions evolve. Prioritize optimizing query predicates, refactoring non-SARGable logic, updating database statistics, or adjusting index coverage before locking in a query hint.
Q29. What core metrics and system tools do you check to evaluate SQL Server production instance performance bottlenecks?
Analyze system performance across two main vectors:
  • Wait Statistics (sys.dm_os_wait_stats): Identify what query threads are waiting for during execution blocks. Focus on indicators like PAGEIOLATCH_* (disk storage bottlenecks), CXPACKET (parallel scheduling overhead from missing indexes), and LCK_M_* (concurrency blocking).
  • Performance Counters: Monitor the Buffer Cache Hit Ratio (percentage of page reads pulled directly from memory cache vs disk; should hover $>95\%$) and **Page Life Expectancy (PLE)** to spot internal memory pressure constraints.
Q30. Explain the schema layout required to build an Event Sourcing model at the storage tier.
An Event Sourcing architecture mandates a strictly append-only database layout. Tables record individual historical changes as immutable event snapshots rather than modifying existing row columns. The schema requires an EventId (Primary Key), AggregateId (the tracking entity key, e.g., OrderId), Version (a sequential counter used to enforce optimistic concurrency validation checks), EventType (e.g., OrderCreated), Timestamp, and a Payload column (typically storing the complete context as a native JSON object). To optimize read performance over long event logs, pair this setup with a periodic snapshotting mechanism to store flattened entity checkpoints.
