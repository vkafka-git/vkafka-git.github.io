Async/Await Internals in C#

1. What Async/Await Does

async/await is syntactic sugar that makes asynchronous code look synchronous. Internally, the C# compiler transforms an async method into a state machine. When you await a Task:

  • It checks if the task is complete.
  • If not, it returns control to the caller (freeing the thread).
  • It registers a continuation so that when the task completes, execution resumes after the await.

This enables non-blocking I/O and allows servers to handle thousands of concurrent requests efficiently.

2. Real-World Example: Web API Calling External Services

Without Async/Await (Blocking)

public ProductResponse GetProduct(int id)
{
    var details = productService.GetDetails(id);   // blocks thread
    var price = pricingService.GetPrice(id);       // blocks thread

    return new ProductResponse(details, price);
}

Each call blocks a thread until the service responds. Under heavy load, threads get exhausted, leading to poor scalability.

With Async/Await (Non-Blocking)

public async Task<ProductResponse> GetProductAsync(int id)
{
    var detailsTask = productService.GetDetailsAsync(id);
    var priceTask = pricingService.GetPriceAsync(id);

    await Task.WhenAll(detailsTask, priceTask);

    return new ProductResponse(detailsTask.Result, priceTask.Result);
}

Here, both service calls start concurrently. await Task.WhenAll frees the thread while waiting. When both tasks finish, the state machine resumes execution and combines results.

3. Internal Mechanics

  • The compiler generates a hidden class implementing a state machine.
  • Each await point becomes a state transition.
  • Continuation delegates are registered with the awaited task.
  • When the task completes, the continuation resumes execution at the correct state.

4. Interview Insight

“async/await in C# compiles into a state machine that frees threads while waiting for tasks. When you await a task, the method returns control to the caller until the task completes, then resumes execution. For example, in a Web API, I can call GetDetailsAsync and GetPriceAsync concurrently, then await Task.WhenAll. This lets the server handle thousands of requests without blocking threads, improving scalability and responsiveness.”

EF Core Concurrency Handling

1. Optimistic Concurrency (Default Approach)

EF Core assumes conflicts are rare and doesn’t lock rows upfront. A property (often RowVersion or [Timestamp]) is marked as a concurrency token. When saving, EF Core includes this token in the WHERE clause of UPDATE/DELETE. If the token has changed (another user updated the row), the update fails, triggering a DbUpdateConcurrencyException. 

public class Person
{
    public int PersonId { get; set; }
    public string FirstName { get; set; }
    [Timestamp]
    public byte[] Version { get; set; } // concurrency token
}

UPDATE [People]
SET [FirstName] = @p0
WHERE [PersonId] = @p1 AND [Version] = @p2;

2. Handling Concurrency Conflicts

You catch DbUpdateConcurrencyException and decide whether to retry, merge, or discard changes. 

try
{
    await context.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    foreach (var entry in ex.Entries)
    {
        var databaseValues = await entry.GetDatabaseValuesAsync();
        entry.OriginalValues.SetValues(databaseValues); // Store wins
    }
    await context.SaveChangesAsync();
}

3. Pessimistic Concurrency (Locking)

EF Core does not provide built-in support for pessimistic concurrency. If required, use raw SQL or stored procedures with SELECT ... FOR UPDATE. This prevents conflicts but reduces scalability.

4. Best Practices

  • Always use a RowVersion/Timestamp column for concurrency tokens in SQL Server.
  • Handle DbUpdateConcurrencyException gracefully — don’t just retry blindly.
  • Log conflicts for audit purposes in compliance-heavy systems.
  • Use optimistic concurrency for most scenarios; reserve pessimistic locking for critical workflows.

Interview Tip

“EF Core uses optimistic concurrency by default. We configure a RowVersion column as a concurrency token, so updates succeed only if the row hasn’t changed since it was read. If a conflict occurs, EF Core throws DbUpdateConcurrencyException, and we handle it by retrying, discarding, or merging changes depending on business rules. For critical workflows, we sometimes fall back to database-level locking via raw SQL.”

RowVersion in EF Core

1. Database-Generated Value

In SQL Server, RowVersion (or Timestamp) is a special column type. The database automatically updates this value every time a row is modified. You don’t supply it from the client — EF Core reads it after an insert/update.

2. EF Core Usage

When marked with [Timestamp], EF Core includes the property in the WHERE clause of updates/deletes. If another update has changed the row, the RowVersion no longer matches, and EF Core throws DbUpdateConcurrencyException.

3. Adding RowVersion to Model

Yes, you add a property in your entity class to represent the column. 

public class Person
{
    public int PersonId { get; set; }
    public string FirstName { get; set; }

    [Timestamp] // Marks as concurrency token
    public byte[] RowVersion { get; set; }
}

4. How It Is Populated

  • On insert: SQL Server generates the initial RowVersion.
  • On update: SQL Server increments it.
  • EF Core retrieves the new value after SaveChanges() and updates your entity’s RowVersion property.
  • You never manually set it — it’s always database-driven.

Interview Tip

“We use a RowVersion column as a concurrency token. EF Core includes it in the WHERE clause during updates. If the value has changed, EF Core throws a DbUpdateConcurrencyException. The database generates and updates the RowVersion automatically, and EF Core refreshes the property after each save. This way, we don’t rely on the client to supply concurrency values.”

Entity Framework Core: Loading Strategies

1. Eager Loading

Eager loading retrieves related data immediatelyInclude() method to specify related entities. 

var orders = context.Orders
    .Include(o => o.Customer)
    .Include(o => o.Items)
    .ToList();

Pros: Reduces round-trips to the database, good for scenarios where related data is always needed.
Cons: Can load unnecessary data, impacting performance if relationships are large.

2. Lazy Loading

Lazy loading retrieves related data only when it is accessed 

var order = context.Orders.First();
var customer = order.Customer; // triggers a query only when accessed

Pros: Loads data only when needed, reducing initial query cost.
Cons: Can cause the "N+1 query problem" if related entities are accessed in loops.

3. Explicit Loading

Explicit loading retrieves related data on demandEntry() API. It gives full control over when related entities are loaded. 

var order = context.Orders.First();
context.Entry(order)
       .Collection(o => o.Items)
       .Load();

Pros: Fine-grained control, avoids unnecessary data loading.
Cons: Requires more code and careful handling to avoid multiple queries.

Interview Insight

“Eager loading uses Include() to fetch related data upfront, lazy loading fetches it only when accessed, and explicit loading gives manual control via Entry().Load(). I choose eager loading when related data is always required, lazy loading for occasional access, and explicit loading when I need precise control over queries.”

Difference between Task, ValueTask, and Thread in C#

1. Task

A Task represents an asynchronous operation. It is part of the Task Parallel Library (TPL) and is typically used with async/await. Tasks can run on thread pool threads and are optimized for managing asynchronous workflows. 

// Example: Task with async/await
public async Task GetDataAsync()
{
    await Task.Delay(1000); // non-blocking wait
    return 42;
}

Pros: Integrates with async/await, supports continuations, cancellation, and exception handling.
Cons: Allocates an object even for trivial operations.

2. ValueTask

A ValueTask is a lightweight alternative to Task. It avoids allocations when the result is already available synchronously. It can represent either a completed result or a pending asynchronous operation. 

// Example: ValueTask
public ValueTask GetCachedDataAsync(bool fromCache)
{
    if (fromCache)
        return new ValueTask(42); // no allocation
    else
        return new ValueTask(Task.Run(() => 42));
}

Pros: Reduces allocations when results are often available synchronously.
Cons: More complex to use; should not be awaited multiple times; best for performance-critical scenarios.

3. Thread

A Thread represents a physical OS thread. It is lower-level than Task and ValueTask. Threads are expensive to create and manage, and they block system resources while running. 

// Example: Thread
var thread = new Thread(() =>
{
    Console.WriteLine("Running on a new thread");
});
thread.Start();

Pros: Full control over execution, suitable for long-running or dedicated operations.
Cons: High overhead, limited scalability, not integrated with async/await.

Comparison Table

Aspect Task ValueTask Thread
Abstraction Level High-level async operation High-level, lightweight async operation Low-level OS thread
Integration with async/await Yes Yes (with caveats) No
Allocation Always allocates Can avoid allocation Expensive to create
Use Case General async workflows Performance-critical, often synchronous results Dedicated long-running operations

Interview Insight

“Task is the standard abstraction for async operations, ValueTask is an optimization to reduce allocations when results are often synchronous, and Thread is a low-level construct representing an OS thread. In modern C#, I use Task for most async workflows, ValueTask for performance-critical scenarios, and Thread only when I need full control over execution.”

Enforcing SOLID Principles in a Large Codebase

1. Single Responsibility Principle (SRP)

  • Code Reviews: Ensure classes have one clear responsibility. Split classes that mix business logic, persistence, and UI concerns.
  • Service Layering: Separate domain logic, application services, and infrastructure code.
  • Static Analysis: Use tools like SonarQube or Roslyn analyzers to detect classes with excessive dependencies or lines of code.

2. Open/Closed Principle (OCP)

  • Design Patterns: Apply Strategy, Factory, and Decorator patterns to extend behavior without modifying existing code.
  • Interfaces & Abstractions: Define abstractions for extensible modules (e.g., payment providers, notification channels).
  • Plug-in Architecture: Use dependency injection to register new implementations without touching core logic.

3. Liskov Substitution Principle (LSP)

  • Inheritance Checks: Ensure derived classes honor base class contracts (no unexpected exceptions or altered semantics).
  • Unit Tests: Write polymorphism tests to confirm substitutability of derived classes.
  • Code Reviews: Flag violations where subclasses weaken preconditions or strengthen postconditions.

4. Interface Segregation Principle (ISP)

  • Modular Interfaces: Avoid “fat” interfaces. Split them into smaller, role-specific contracts.
  • Dependency Injection: Inject only the interfaces needed by a class.
  • Static Analysis: Detect unused interface members to identify bloated contracts.

5. Dependency Inversion Principle (DIP)

  • Abstractions First: High-level modules depend on interfaces, not concrete classes.
  • IoC Containers: Use DI frameworks (e.g., Microsoft.Extensions.DependencyInjection, Autofac) to wire dependencies.
  • Testing: Mock abstractions in unit tests to decouple from infrastructure.

Cross-Cutting Enforcement Strategies

  • Automated Code Quality: StyleCop, Roslyn analyzers, and SonarQube enforce coding standards aligned with SOLID.
  • Architecture Governance: Define clear layering rules (Domain → Application → Infrastructure) and enforce them via tools like ArchUnit.NET.
  • Continuous Integration: Integrate static analysis and unit tests into CI/CD pipelines to catch violations early.
  • Mentorship & Reviews: Senior developers guide juniors during design reviews, ensuring adherence to SOLID principles.

Interview Insight

“In a large codebase, enforcing SOLID principles requires a mix of technical tools and cultural practices. We use static analysis and CI/CD pipelines to detect violations, design patterns and abstractions to enable extensibility, and code reviews plus mentorship to ensure developers consistently apply SRP, OCP, LSP, ISP, and DIP. This combination keeps the system maintainable, testable, and scalable.”

Designing Multi-Region Deployments

1. Goals of Multi-Region Architecture

  • High Availability: Survive regional outages by failing over to another region.
  • Disaster Recovery: Ensure business continuity with RTO (Recovery Time Objective) and RPO (Recovery Point Objective) targets.
  • Low Latency: Serve users from the nearest region to reduce response times.
  • Compliance: Meet data residency requirements by storing data in specific regions.

2. Core Design Patterns

  • Active-Passive: One primary region handles traffic, another region is on standby for failover.
  • Active-Active: Multiple regions serve traffic simultaneously, often with global load balancing.
  • Pilot Light: Minimal infrastructure in secondary region, scaled up only during disaster recovery.

3. Key Components

  • Global Load Balancing: Use Azure Front Door, AWS Route 53, or GCP Cloud Load Balancing to route traffic to the nearest healthy region.
  • Data Replication:
    • Relational DB: Use geo-replication (Azure SQL, Amazon RDS).
    • NoSQL DB: Use multi-region replication (Cosmos DB, DynamoDB).
    • Blob/Object Storage: Enable geo-redundant storage (GRS, S3 Cross-Region Replication).
  • State Management: Design stateless services; store session state in distributed caches (Redis, DynamoDB, Cosmos DB).
  • CI/CD Pipelines: Deploy consistently across regions using Infrastructure as Code (Terraform, Bicep, CloudFormation).

4. Cross-Cutting Concerns

  • Security: Apply Zero-Trust principles, private endpoints, and region-specific compliance policies.
  • Observability: Centralized logging and monitoring across regions (Azure Monitor, AWS CloudWatch, Grafana).
  • Resilience: Implement health probes, automatic failover, and chaos testing to validate recovery.
  • Cost Optimization: Balance redundancy with cost; active-active is more expensive than active-passive.

5. Example Flow

  1. User request hits global DNS/load balancer.
  2. Traffic routed to nearest region (e.g., East US, West Europe, Southeast Asia).
  3. Microservices deployed in AKS/EKS clusters in each region handle requests.
  4. Data replicated across regions using geo-replication.
  5. If a region fails, traffic automatically reroutes to another healthy region.

Interview Insight

“In multi-region deployments, I design for high availability and disaster recovery using active-active or active-passive patterns. I rely on global load balancing, geo-replication for databases, and stateless microservices to ensure resilience. Observability and Zero-Trust security are enforced across all regions. The trade-off is cost versus availability, so I align the architecture with business RTO/RPO requirements.”

Rollback Strategy for Failed Production Deployments

1. Guiding Principles

  • Minimize Downtime: Rollback should be fast and automated to restore service quickly.
  • Data Integrity: Ensure database schema and data remain consistent during rollback.
  • Predictability: Rollback paths must be tested and documented, not improvised.

2. Rollback Approaches

  • Blue-Green Deployment: Maintain two environments (Blue = current, Green = new). If Green fails, traffic is switched back to Blue instantly.
  • Canary Release: Deploy to a small subset of users. If issues arise, rollback affects only the canary group before wider rollout.
  • Deployment Slots: In Azure App Service or Kubernetes, use slots/namespaces. Swap back to the previous slot if the new one fails.
  • Immutable Artifacts: Store versioned container images and packages. Rollback simply redeploys the last known good artifact.

3. Database Rollback

  • Backward-Compatible Migrations: Apply additive changes (new columns, tables) instead of destructive ones.
  • Feature Flags: Toggle features off if schema changes are not reversible.
  • Point-in-Time Restore: Use database backups or snapshots for critical failures.

4. Automation in CI/CD

  • Pipeline Integration: Rollback steps scripted into Azure DevOps or GitHub Actions pipelines.
  • Monitoring & Alerts: Automated rollback triggered by health probes, SLA breaches, or error thresholds.
  • Version Control: Tag and store every release artifact for quick redeployment.

5. Observability During Rollback

  • Centralized Logging: Track rollback events in Elasticsearch/Kibana or Application Insights.
  • Metrics: Monitor latency, error rates, and throughput before and after rollback.
  • Audit Trail: Maintain compliance logs of rollback actions for governance.

6. Interview Insight

“My rollback strategy combines deployment patterns like blue-green and canary releases with automated CI/CD pipelines. If a deployment fails, I can instantly redirect traffic to the last stable version, redeploy previous container images, or restore database snapshots. Rollback is always tested in staging, integrated with monitoring, and designed to minimize downtime while preserving data integrity.”

Repository vs Unit of Work Patterns

Repository Pattern

Purpose: Abstracts data access logic, providing a clean API for the domain layer to interact with persistence.
Focus: Encapsulates queries and CRUD operations for a specific aggregate or entity.

  • Decouples business logic from data access.
  • Makes unit testing easier (repositories can be mocked).
  • Centralizes query logic for consistency.
public interface ICustomerRepository
{
    Customer GetById(int id);
    IEnumerable<Customer> GetAll();
    void Add(Customer customer);
    void Remove(Customer customer);
}

public class CustomerRepository : ICustomerRepository
{
    private readonly AppDbContext _context;
    public CustomerRepository(AppDbContext context) => _context = context;

    public Customer GetById(int id) => _context.Customers.Find(id);
    public IEnumerable<Customer> GetAll() => _context.Customers.ToList();
    public void Add(Customer customer) => _context.Customers.Add(customer);
    public void Remove(Customer customer) => _context.Customers.Remove(customer);
}

Unit of Work Pattern

Purpose: Coordinates changes across multiple repositories, ensuring they are committed as a single transaction.
Focus: Manages the lifecycle of a transaction and aggregates repository operations.

  • Ensures consistency when multiple repositories are involved.
  • Provides a single Commit() or SaveChanges() method to persist changes.
  • Reduces the risk of partial updates.
public interface IUnitOfWork : IDisposable
{
    ICustomerRepository Customers { get; }
    IOrderRepository Orders { get; }
    int Complete();
}

public class UnitOfWork : IUnitOfWork
{
    private readonly AppDbContext _context;
    public ICustomerRepository Customers { get; }
    public IOrderRepository Orders { get; }

    public UnitOfWork(AppDbContext context)
    {
        _context = context;
        Customers = new CustomerRepository(_context);
        Orders = new OrderRepository(_context);
    }

    public int Complete() => _context.SaveChanges();
    public void Dispose() => _context.Dispose();
}

Key Differences

Aspect Repository Unit of Work
Scope Single entity/aggregate Multiple repositories/transaction
Responsibility Encapsulates CRUD/query logic Coordinates repositories + commits
Transaction Not responsible Ensures atomic commits across repos
Usage Access data in a clean way Manage consistency across operations

👉 Think of Repository as the data access abstraction and Unit of Work as the transaction manager. Together, they form a powerful combination: repositories handle entity-specific operations, while the unit of work ensures everything is committed consistently.

Difference between IEnumerable, IQueryable, and List in C#

1. IEnumerable<T>

Execution: In-memory (LINQ-to-Objects).
Deferred: Yes, filters are applied when iterated.
Use Case: Iterate/filter already-loaded collections. 

IEnumerable<Product> products = context.Products.ToList();
var activeProducts = products.Where(p => p.IsActive); // filtering in memory

👉 Loads all products first, then filters locally. Good for small datasets.

2. IQueryable<T>

Execution: Translated to SQL / remote source.
Deferred: Yes, query built and executed on DB.
Use Case: Query large datasets efficiently. 

IQueryable<Product> products = context.Products;
var activeProducts = products.Where(p => p.IsActive).ToList();

👉 Where is translated into SQL (SELECT * FROM Products WHERE IsActive = 1). Efficient for large datasets.

3. List<T>

Execution: Immediate, in-memory.
Deferred: No, data already loaded.
Use Case: Store/manipulate concrete data. 

List<Product> products = new List<Product>
{
    new Product { Id = 1, Name = "Laptop" },
    new Product { Id = 2, Name = "Phone" }
};

👉 A concrete collection in memory. You can add/remove items directly.

Comparison Table

Aspect IEnumerable<T> IQueryable<T> List<T>
Execution In-memory Database / remote source Immediate, in-memory
Deferred? Yes Yes No
Use Case Filter already-loaded data Efficient DB queries Mutable collection
Performance Can be inefficient for large DB sets Optimized, server-side filtering Fast for local operations
Mutability Read-only iteration Read-only query abstraction Fully mutable (Add/Remove)

👉 IEnumerable is for in-memory iteration, IQueryable builds queries that run on the database, and List is a concrete collection type.

Dependency Injection in ASP.NET Core

1. What is Dependency Injection?

Dependency Injection (DI) is a design pattern that allows classes to declare their dependencies instead of creating them directly. ASP.NET Core has a built-in DI container that manages object lifetimes and resolves dependencies automatically.

2. How It Works

  • Registration: Services are registered in the DI container inside Program.cs or Startup.cs using methods like AddSingleton, AddScoped, and AddTransient.
  • Resolution: When a class (e.g., Controller, Service) requires a dependency, ASP.NET Core automatically provides it via constructor injection.
  • Lifetime Management: The DI container controls how long a service instance lives (singleton, scoped, transient).

3. Service Lifetimes

  • Singleton: One instance for the entire application lifetime.
  • Scoped: One instance per request (web request scope).
  • Transient: A new instance every time it is requested.

4. Example

// Register services in Program.cs
builder.Services.AddSingleton<ILoggingService, LoggingService>();
builder.Services.AddScoped<IRepository, Repository>();
builder.Services.AddTransient<INotificationService, EmailNotificationService>();

// Use dependency injection in a Controller
public class OrdersController : Controller
{
    private readonly IRepository _repository;
    private readonly INotificationService _notification;

    public OrdersController(IRepository repository, INotificationService notification)
    {
        _repository = repository;
        _notification = notification;
    }

    public IActionResult CreateOrder(Order order)
    {
        _repository.Add(order);
        _notification.Send("Order created successfully!");
        return Ok();
    }
}

5. Benefits

  • Promotes loose coupling between classes.
  • Makes unit testing easier (dependencies can be mocked).
  • Centralizes configuration of services.
  • Improves maintainability and scalability of applications.

6. Interview Insight

👉 In ASP.NET Core, DI is first-class and built-in. You don’t need external frameworks like Autofac or Ninject unless you want advanced features. Always mention lifetimes (Singleton, Scoped, Transient) and constructor injection when explaining DI in interviews.

Middleware Pipeline in ASP.NET Core

1. What is Middleware?

Middleware are components in ASP.NET Core that process HTTP requests and responses. Each middleware can perform operations before and after passing control to the next middleware in the pipeline.

2. How the Pipeline Works

  • Requests enter the pipeline and pass through each middleware in sequence.
  • Each middleware decides whether to:
    • Process the request and pass it to the next middleware.
    • Short-circuit the pipeline (e.g., return a response immediately).
  • Responses travel back through the pipeline in reverse order.

3. Middleware Registration

Middleware is registered in Program.cs or Startup.cs using the app.Use... methods. 

// Example pipeline setup in Program.cs
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();

app.UseEndpoints(endpoints =>
{
    endpoints.MapControllers();
});

app.Run();

4. Custom Middleware Example

public class LoggingMiddleware
{
    private readonly RequestDelegate _next;

    public LoggingMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        Console.WriteLine($"Request: {context.Request.Path}");
        await _next(context); // Call the next middleware
        Console.WriteLine($"Response: {context.Response.StatusCode}");
    }
}

// Register custom middleware
app.UseMiddleware<LoggingMiddleware>();

5. Common Middleware Components

  • UseRouting: Matches incoming requests to endpoints.
  • UseAuthentication: Validates user identity.
  • UseAuthorization: Enforces access policies.
  • UseStaticFiles: Serves static content like CSS, JS, images.
  • UseExceptionHandler: Handles errors globally.

6. Interview Insight

👉 The middleware pipeline is ordered and sequential. The order of registration matters — for example, UseRouting must come before UseEndpoints, and UseAuthentication must come before UseAuthorization. Always emphasize that middleware can both handle requests and modify responses.

Global Exception Handling in ASP.NET Core

1. Why Global Exception Handling?

Global exception handling ensures that unhandled errors are caught in one place, logged, and returned with a consistent response format. This prevents application crashes and improves reliability, security, and user experience.

2. Approaches

  • UseExceptionHandler Middleware: Built-in middleware to handle exceptions globally.
  • DeveloperExceptionPage: Shows detailed error info during development.
  • Custom Middleware: Create your own middleware to catch and log exceptions.
  • Exception Filters: In MVC/Web API, filters can handle exceptions at the controller/action level.

3. Using Built-in Middleware

// Program.cs
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/Home/Error"); // Redirect to error page
    app.UseHsts();
}

app.Run();

4. Custom Middleware Example

public class GlobalExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<GlobalExceptionMiddleware> _logger;

    public GlobalExceptionMiddleware(RequestDelegate next, ILogger<GlobalExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context); // Call next middleware
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Unhandled exception occurred");
            context.Response.StatusCode = 500;
            context.Response.ContentType = "application/json";
            await context.Response.WriteAsync(
                $"{{\"error\":\"An unexpected error occurred.\"}}"
            );
        }
    }
}

// Register custom middleware
app.UseMiddleware<GlobalExceptionMiddleware>();

5. Exception Filters (MVC/Web API)

public class GlobalExceptionFilter : IExceptionFilter
{
    private readonly ILogger<GlobalExceptionFilter> _logger;

    public GlobalExceptionFilter(ILogger<GlobalExceptionFilter> logger)
    {
        _logger = logger;
    }

    public void OnException(ExceptionContext context)
    {
        _logger.LogError(context.Exception, "Unhandled exception");
        context.Result = new ObjectResult("An error occurred")
        {
            StatusCode = 500
        };
    }
}

// Register filter globally
services.AddControllers(options =>
{
    options.Filters.Add<GlobalExceptionFilter>();
});

6. Best Practices

  • Log exceptions with sufficient context (user, request, stack trace).
  • Return generic error messages to clients (avoid exposing sensitive details).
  • Use structured logging (e.g., Serilog, NLog) for better observability.
  • Test exception handling paths during deployment.

7. Interview Insight

👉 In ASP.NET Core, global exception handling is typically implemented using UseExceptionHandler or custom middleware. For APIs, exception filters provide fine-grained control. Always emphasize logging, consistent error responses, and security (no sensitive info in error messages).

Difference between AddScoped, AddTransient, and AddSingleton

1. AddTransient

Lifetime: A new instance is created every time it is requested.
Use Case: Lightweight, stateless services where creating a new object is inexpensive. 

// Registration
builder.Services.AddTransient<IMailService, MailService>();

// Usage
public class NotificationController : Controller
{
    private readonly IMailService _mailService;
    public NotificationController(IMailService mailService)
    {
        _mailService = mailService; // new instance each time
    }
}

2. AddScoped

Lifetime: One instance per request (scope). Within a single HTTP request, the same instance is reused.
Use Case: Services that should maintain state during a request but not across requests. 

// Registration
builder.Services.AddScoped<IOrderService, OrderService>();

// Usage
public class OrdersController : Controller
{
    private readonly IOrderService _orderService;
    public OrdersController(IOrderService orderService)
    {
        _orderService = orderService; // same instance within one request
    }
}

3. AddSingleton

Lifetime: A single instance is created and shared across the entire application lifetime.
Use Case: Services that are expensive to create or need to maintain global state (e.g., caching, configuration). 

// Registration
builder.Services.AddSingleton<ICacheService, MemoryCacheService>();

// Usage
public class ProductsController : Controller
{
    private readonly ICacheService _cacheService;
    public ProductsController(ICacheService cacheService)
    {
        _cacheService = cacheService; // same instance for all requests
    }
}

4. Comparison Table

Aspect AddTransient AddScoped AddSingleton
Lifetime New instance every time One instance per request One instance for entire app
Performance Lightweight, stateless Balanced, request-scoped Best for heavy/global services
State No state maintained State maintained within request State maintained globally
Examples Utility services, helpers Repository, Unit of Work Configuration, caching, logging

5. Interview Insight

👉 In ASP.NET Core, AddTransient is for short-lived, stateless services, AddScoped is for request-specific services, and AddSingleton is for global services shared across the application. Always emphasize that choosing the right lifetime is critical to avoid memory leaks, concurrency issues, or unintended shared state.

Securing APIs with JWT in ASP.NET Core

1. What is JWT?

JWT (JSON Web Token) is a compact, URL-safe token used for authentication and authorization. It consists of three parts: Header (algorithm, type), Payload (claims like user ID, roles), and Signature (validates integrity).

2. How JWT Secures APIs

  • Authentication: After login, the server issues a signed JWT to the client.
  • Authorization: The client sends the JWT in the Authorization: Bearer <token> header for each API request.
  • Validation: The API validates the token’s signature, issuer, audience, and expiration before granting access.

4. Creating JWT Tokens

using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using Microsoft.IdentityModel.Tokens;

public class JwtService
{
    private readonly IConfiguration _config;
    public JwtService(IConfiguration config) => _config = config;

    public string GenerateToken(string userId, string role)
    {
        var claims = new[]
        {
            new Claim(ClaimTypes.NameIdentifier, userId),
            new Claim(ClaimTypes.Role, role)
        };

        var key = new SymmetricSecurityKey(
            Encoding.UTF8.GetBytes(_config["Jwt:Key"]));
        var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

        var token = new JwtSecurityToken(
            issuer: _config["Jwt:Issuer"],
            audience: _config["Jwt:Audience"],
            claims: claims,
            expires: DateTime.Now.AddMinutes(60),
            signingCredentials: creds);

        return new JwtSecurityTokenHandler().WriteToken(token);
    }
}

LINQ Deferred Execution in C#

1. What is Deferred Execution?

Deferred execution means that a LINQ query is not executed at the moment it is defined. Instead, it is executed only when the query results are actually iterated (e.g., using foreach, ToList(), or Count()). This allows LINQ to build query expressions and delay execution until needed.

2. How It Works

  • When you write a LINQ query, it creates a query object, not the actual results.
  • The query is executed only when you enumerate it.
  • This enables optimizations like combining filters and avoiding unnecessary work.

3. Example of Deferred Execution

List<int> numbers = new List<int> { 1, 2, 3, 4, 5 };

// LINQ query defined but not executed yet
var query = numbers.Where(n => n > 2);

// Modify the source before execution
numbers.Add(6);

// Execution happens here (iteration)
foreach (var n in query)
{
    Console.WriteLine(n);
}

👉 Output will be 3, 4, 5, 6 because the query executes at iteration time, after the list was modified.

4. Immediate Execution

If you want to force execution immediately, you can use methods like ToList(), ToArray(), or Count(). 

var result = numbers.Where(n => n > 2).ToList(); // executes immediately

5. Benefits of Deferred Execution

  • Improves performance by delaying work until necessary.
  • Allows queries to reflect the latest state of the data source.
  • Enables query composition (adding filters before execution).

6. Risks

  • Source data changes may lead to unexpected results if not understood properly.
  • Multiple iterations re-execute the query unless results are cached with ToList().

7. Interview Insight

👉 In interviews, emphasize that LINQ queries are deferred by default, meaning they execute only when enumerated. Mention that ToList() or ToArray() forces immediate execution, and highlight the trade-off between flexibility and performance.

Designing an Idempotent REST API

1. What Does Idempotent Mean?

An operation is idempotent if performing it multiple times has the same effect as performing it once. In REST APIs, this ensures that repeated requests (due to retries, network issues, or client errors) do not cause unintended side effects.

2. HTTP Methods and Idempotency

  • GET: Always idempotent. Fetching the same resource multiple times does not change state.
  • PUT: Idempotent. Updating a resource with the same data repeatedly results in the same final state.
  • DELETE: Idempotent. Deleting a resource multiple times leaves the system in the same state (resource gone).
  • POST: Not idempotent by default. Each call usually creates a new resource, but can be designed to be idempotent using unique identifiers or idempotency keys.

3. Design Strategies

  • Use Resource Identifiers: Ensure clients provide unique IDs (e.g., order ID) so repeated requests update the same resource instead of creating duplicates.
  • Idempotency Keys: Accept a unique key in headers (e.g., Idempotency-Key) to detect duplicate requests and return the same response.
  • PUT vs POST: Use PUT for updates (idempotent) and design POST carefully if retries are expected.
  • Safe Deletes: Implement soft deletes or return consistent responses when a resource is already deleted.
  • Consistent Responses: Always return the same result for repeated identical requests.

4. Example: Idempotent Order Creation

// Client sends POST with Idempotency-Key
POST /orders
Headers: Idempotency-Key: abc123

{
  "orderId": "ORD001",
  "productId": "P100",
  "quantity": 2
}

// Server checks if Idempotency-Key already processed
// If yes, return same response without creating duplicate

5. Benefits

  • Prevents duplicate resource creation.
  • Improves reliability in distributed systems.
  • Supports retry logic in clients and API gateways.
  • Ensures predictable outcomes for consumers.

Strategies to Ensure Backward Compatibility in APIs

1. Why Backward Compatibility Matters

Backward compatibility ensures that existing API consumers continue to function correctly even after new versions or changes are introduced. It prevents breaking changes that could disrupt client applications and guarantees a stable integration experience.

2. Key Strategies

  • Versioning: Introduce new versions (e.g., /v1/orders, /v2/orders) instead of modifying existing endpoints.
  • Additive Changes: Add new fields or endpoints rather than removing or renaming existing ones.
  • Default Values: Provide sensible defaults for new fields so older clients can continue without modification.
  • Deprecation Policy: Mark features as deprecated before removal, and give clients time to migrate.
  • Contract Testing: Use schema validation (JSON Schema, OpenAPI) to ensure responses remain compatible.
  • Feature Flags: Introduce new behavior behind flags so clients can opt-in gradually.
  • Graceful Error Handling: Return consistent error formats and avoid introducing new mandatory fields suddenly.

Monolith vs Microservices: Trade-offs

1. Monolithic Architecture

A monolith is a single, unified codebase where all modules (UI, business logic, data access) are tightly coupled and deployed together.

Advantages

  • Simplicity: Easier to develop, test, and deploy initially.
  • Performance: Direct function calls, no network overhead between modules.
  • Tooling: Mature frameworks and simpler CI/CD pipelines.
  • Consistency: Shared memory and state across modules.

Disadvantages

  • Scalability: Cannot scale individual components independently.
  • Maintainability: Large codebase becomes hard to manage over time.
  • Deployment: Any change requires redeploying the entire application.
  • Reliability: A bug in one module can crash the whole system.

2. Microservices Architecture

Microservices break the application into small, independent services that communicate via APIs (REST, gRPC, messaging).

Advantages

  • Scalability: Scale services independently based on demand.
  • Flexibility: Different services can use different technologies.
  • Deployment: Deploy and update services independently.
  • Resilience: Failures are isolated to individual services.
  • Team Autonomy: Teams can own and manage services independently.

Disadvantages

  • Complexity: Requires service discovery, API gateways, and orchestration.
  • Performance: Network latency and serialization overhead.
  • Data Management: Distributed data consistency is harder to achieve.
  • DevOps Overhead: Requires CI/CD, monitoring, logging, and scaling infrastructure.

Aspect Monolith Microservices

Scalability Whole app only Per-service scaling
Complexity Low High (distributed system)
Performance Fast (in-process calls) Slower (network calls)

Circuit Breaker Pattern in Microservices

1. What is the Circuit Breaker Pattern?

The Circuit Breaker pattern is a resilience strategy used in distributed systems to prevent cascading failures. It monitors calls to external services and "opens" the circuit if failures exceed a threshold, temporarily blocking further calls until the service recovers.

2. Why Use It?

  • Protects the system from repeated failures when a dependency is down.
  • Prevents resource exhaustion (threads, memory, CPU).
  • Improves fault tolerance and user experience by failing fast.

3. States of a Circuit Breaker

  • Closed: Normal operation. Requests flow through. Failures are counted.
  • Open: The circuit trips after threshold failures. Requests are blocked immediately.
  • Half-Open: After a timeout, a limited number of test requests are allowed. If successful, the circuit closes; if not, it reopens.

4. Example in .NET with Polly

using Polly;
using Polly.CircuitBreaker;

var circuitBreakerPolicy = Policy
    .Handle<HttpRequestException>()
    .CircuitBreaker(
        exceptionsAllowedBeforeBreaking: 3,
        durationOfBreak: TimeSpan.FromSeconds(30)
    );

try
{
    circuitBreakerPolicy.Execute(() =>
    {
        // Call external API
        var response = httpClient.GetAsync("https://external-service/api/data").Result;
        response.EnsureSuccessStatusCode();
    });
}
catch (BrokenCircuitException)
{
    Console.WriteLine("Circuit is open. Failing fast.");
}

5. Business Scenario Example

Imagine an immigration service API that frequently becomes unstable. Instead of retrying endlessly and slowing down the system, the circuit breaker blocks calls once failures exceed a threshold. After a cooldown period, it allows test calls to check if the API is healthy again.

6. Best Practices

  • Combine with Retry policies for transient failures.
  • Log and monitor circuit breaker state changes.
  • Use fallback responses (e.g., cached data, default values).
  • Configure thresholds carefully to balance resilience and availability.

7. Interview Insight

AKS, Clusters, Nodes, Pods, and Containers

1. AKS (Azure Kubernetes Service)

AKS is a managed Kubernetes service provided by Microsoft Azure. It abstracts the complexity of setting up and maintaining Kubernetes clusters, offering built-in scaling, monitoring, and integration with Azure services.

2. Cluster

A Kubernetes cluster is the overall environment that runs containerized applications. It consists of:

  • Control Plane: Manages the cluster, schedules workloads, and maintains desired state.
  • Worker Nodes: Machines (VMs) where workloads (pods) run.

3. Node

A node is a single machine (physical or virtual) inside the cluster. Each node runs:

  • Kubelet: Agent that communicates with the control plane.
  • Container Runtime: (e.g., Docker, containerd) to run containers.
  • Kube-proxy: Handles networking for pods.

4. Pod

A pod is the smallest deployable unit in Kubernetes. It wraps one or more containers that share networking and storage. Pods are ephemeral — they can be created, destroyed, and rescheduled by Kubernetes.

5. Container

A container is the actual runtime unit that packages an application and its dependencies. It ensures consistent execution across environments. Containers are created from images (e.g., Docker images) and run inside pods.

6. Other Related Terminology

  • Deployment: Defines how many replicas of a pod should run and manages rolling updates.
  • Service: Provides a stable network endpoint to access pods, even if pods change.
  • Ingress: Manages external access (HTTP/HTTPS) to services inside the cluster.
  • Namespace: Logical grouping of resources inside a cluster for isolation.
  • ReplicaSet: Ensures a specified number of pod replicas are running at all times.

7. Hierarchy & Interrelation

These concepts are tightly interrelated:

  • AKS → Provides the managed Kubernetes environment.
  • Cluster → The overall system containing control plane + worker nodes.
  • Node → Machines inside the cluster that run workloads.
  • Pod → Smallest deployable unit, running containers on nodes.
  • Container → The actual application running inside the pod.

               └── Pod
                     └── Container (App)

Securing Inter-Service Communication in Microservices

1. Why Secure Inter-Service Communication?

In a microservices architecture, services often communicate over the network. Without proper security, attackers could intercept, spoof, or tamper with messages. Securing inter-service communication ensures confidentiality, integrity, and trust between services.

2. Key Strategies

  • Mutual TLS (mTLS): Both client and server authenticate each other using certificates. Ensures encrypted communication and prevents impersonation.
  • Service Mesh: Tools like Istio, Linkerd, or Consul automatically enforce mTLS, traffic policies, and observability across services.
  • API Gateway: Acts as a secure entry point, enforcing authentication, authorization, and rate limiting before requests reach services.
  • Token-Based Authentication: Use JWT or OAuth2 tokens for identity propagation between services.
  • Network Policies: Restrict which services can talk to each other using Kubernetes Network Policies or cloud VNet rules.
  • Encryption: Always encrypt data in transit (TLS 1.2+). For sensitive data, also encrypt at rest.
  • Zero-Trust Principles: Never assume trust between services; every request must be authenticated and authorized.

3. Example: Mutual TLS in Kubernetes

// Both present certificates signed by a trusted CA
// Communication is encrypted and authenticated

Service A ----mTLS----> Service B

4. Example: JWT Propagation

// It forwards the JWT when calling Service B
// Service B validates the token before processing

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

5. Best Practices

  • Automate certificate rotation and renewal.
  • Use a service mesh for consistent enforcement of security policies.
  • Implement fine-grained RBAC (Role-Based Access Control).
  • Log and monitor inter-service traffic for anomalies.
  • Apply defense-in-depth: combine mTLS, tokens, and network policies.

6. Interview Insight

👉 Securing inter-service communication involves mTLS for encryption and authentication, JWT/OAuth2 for identity propagation, and network policies for isolation. In interviews, emphasize Zero-Trust principles — every request must be verified, even between internal services.

Role of an API Gateway in Microservices

1. What is an API Gateway?

An API Gateway is a single entry point that sits between clients and microservices. It routes requests, enforces policies, and provides cross-cutting concerns like security, monitoring, and rate limiting. Think of it as the "front door" to your microservices ecosystem.

2. Key Responsibilities

  • Request Routing: Directs client requests to the appropriate microservice.
  • Authentication & Authorization: Validates tokens (e.g., JWT, OAuth2) and enforces access control.
  • Rate Limiting & Throttling: Protects services from overload by limiting requests per client.
  • Load Balancing: Distributes traffic across multiple service instances.
  • Protocol Translation: Converts between protocols (e.g., HTTP ↔ gRPC, WebSockets).
  • Caching: Stores frequently accessed responses to improve performance.
  • Monitoring & Logging: Collects metrics and logs for observability.
  • Request/Response Transformation: Modifies headers, payloads, or formats before forwarding.

3. Example Flow

Client → API Gateway → Authentication → Routing → Microservice → Response

4. Common Tools

  • YARP (ASP.NET Core): Lightweight reverse proxy for .NET applications.
  • NGINX / Kong: Popular open-source gateways with plugin ecosystems.
  • Azure API Management: Cloud-native API gateway with enterprise features.
  • Istio (Service Mesh): Provides gateway + service-to-service security.

5. Benefits

  • Simplifies client communication by exposing a unified API surface.
  • Centralizes cross-cutting concerns (security, logging, throttling).
  • Improves scalability and resilience.
  • Enables versioning and backward compatibility strategies.

6. Interview Insight

In interviews, emphasize that it reduces complexity for clients, enforces policies centrally, and integrates with service discovery and load balancing. It’s the backbone of secure and manageable inter-service communication.

Designing Pagination in APIs

1. Why Pagination?

Pagination is used to split large datasets into smaller chunks when returning results from an API. It improves performance, reduces payload size, and provides a better client experience by avoiding overwhelming responses.

2. Common Pagination Strategies

  • Offset-Based: Use limit and offset parameters.
    Example: /api/products?limit=10&offset=20
    Pros: Simple to implement. Cons: Inefficient for large datasets (slow skips).
  • Page-Based: Use page and size parameters.
    Example: /api/products?page=3&size=10
    Pros: Easy for clients. Cons: Can be inconsistent if data changes between requests.
  • Cursor-Based: Use a unique identifier (like timestamp or ID) as a cursor.
    Example: /api/products?after=123&limit=10
    Pros: Efficient for large datasets, consistent results. Cons: More complex to implement.
  • Keyset Pagination: Similar to cursor-based, uses indexed fields for fast lookups.
    Example: /api/products?lastId=200&limit=10
    Pros: Very efficient with indexed columns. Cons: Requires careful schema design.

3. Example: Offset-Based Pagination

// Request
GET /api/orders?limit=5&offset=10

// Response
{
  "data": [
    { "orderId": "ORD011", "status": "Shipped" },
    { "orderId": "ORD012", "status": "Pending" },
    ...
  ],
  "pagination": {
    "limit": 5,
    "offset": 10,
    "total": 100
  }
}

4. Example: Cursor-Based Pagination

// Request
GET /api/orders?after=ORD010&limit=5

// Response
{
  "data": [
    { "orderId": "ORD011", "status": "Shipped" },
    { "orderId": "ORD012", "status": "Pending" },
    ...
  ],
  "pagination": {
    "limit": 5,
    "nextCursor": "ORD015"
  }
}

5. Best Practices

  • Always return metadata (total count, next/previous links, cursors).
  • Use consistent naming conventions (page, size, limit, offset).
  • Prefer cursor-based pagination for large, frequently updated datasets.
  • Support sorting and filtering alongside pagination.
  • Document pagination strategy clearly for API consumers.

6. Interview Insight

Handling Rate Limiting in APIs

1. What is Rate Limiting?

Rate limiting controls how many requests a client can make to an API within a given time window. It protects services from abuse, prevents overload, and ensures fair usage among clients.

2. Common Strategies

  • Fixed Window: Limit requests per fixed interval (e.g., 100 requests per minute). Simple but can cause bursts at window boundaries.
  • Sliding Window: Tracks requests in a rolling time window. More accurate but requires more computation.
  • Token Bucket: Clients accumulate tokens at a fixed rate; each request consumes a token. Allows short bursts while enforcing limits.
  • Leaky Bucket: Similar to token bucket but enforces a steady outflow rate, smoothing traffic.

3. Implementation Approaches

  • API Gateway: Enforce rate limits at the gateway (e.g., Kong, NGINX, Azure API Management).
  • Middleware: Implement rate limiting logic in application middleware (e.g., ASP.NET Core middleware).
  • Distributed Cache: Use Redis or Memcached to track request counts across multiple servers.

4. Example: ASP.NET Core Middleware with Redis

// Pseudocode for fixed window rate limiting
if (redis.Increment("client:123:minute") > 100)
{
    return 429 Too Many Requests;
}
else
{
    processRequest();
}

5. Best Practices

  • Return HTTP 429 Too Many Requests when limits are exceeded.
  • Include Retry-After header to guide clients on when to retry.
  • Differentiate limits by client type (e.g., free vs premium users).
  • Combine with authentication to enforce per-user or per-API key limits.
  • Monitor and log rate limit violations for analysis.

6. Interview Insight

👉 Rate limiting ensures fair usage and system stability. In interviews, emphasize strategies like fixed window, sliding window, token bucket, and mention practical enforcement via API gateways or distributed caches. Highlight the importance of returning proper HTTP status codes and headers for client guidance.

CORS (Cross-Origin Resource Sharing) and Its Configuration

1. What is CORS?

CORS is a security mechanism implemented by browsers to restrict web applications from making requests to a domain different from the one that served the web page. It prevents malicious scripts from accessing sensitive data from another origin. When a client (e.g., JavaScript in a browser) calls an API hosted on a different domain, the server must explicitly allow it via CORS headers.

2. Key Concepts

  • Origin: Defined by scheme (http/https), host, and port. Example: https://example.com:443.
  • Same-Origin Policy: By default, browsers block requests from one origin to another.
  • Preflight Request: For non-simple requests (e.g., PUT, DELETE, custom headers), the browser sends an OPTIONS request first to check if the server allows it.
  • CORS Headers: Server responds with headers like Access-Control-Allow-Origin, Access-Control-Allow-Methods, and Access-Control-Allow-Headers.

3. Common CORS Headers

  • Access-Control-Allow-Origin: Specifies which origins can access the resource (e.g., * or https://myapp.com).
  • Access-Control-Allow-Methods: Lists allowed HTTP methods (e.g., GET, POST, PUT).
  • Access-Control-Allow-Headers: Lists allowed custom headers (e.g., Content-Type, Authorization).
  • Access-Control-Allow-Credentials: Indicates whether cookies/credentials can be sent.

4. Example: ASP.NET Core Configuration

// In Program.cs
builder.Services.AddCors(options =>
{
    options.AddPolicy("AllowSpecificOrigin",
        policy => policy.WithOrigins("https://myapp.com")
                        .AllowAnyHeader()
                        .AllowAnyMethod()
                        .AllowCredentials());
});

var app = builder.Build();
app.UseCors("AllowSpecificOrigin");

5. Example: Express.js Configuration

const cors = require('cors');
const app = require('express')();

app.use(cors({
  origin: 'https://myapp.com',
  methods: ['GET','POST','PUT'],
  allowedHeaders: ['Content-Type','Authorization'],
  credentials: true
}));

6. Best Practices

  • Restrict Access-Control-Allow-Origin to trusted domains (avoid * in production).
  • Allow only necessary methods and headers.
  • Enable credentials only when required.
  • Log and monitor CORS errors for debugging.

Implementing Caching in APIs

1. Why Caching?

Caching improves API performance by storing frequently accessed data closer to the client or server. It reduces latency, minimizes database load, and improves scalability. Without caching, APIs may repeatedly fetch the same data, leading to inefficiency.

2. Types of Caching

  • Client-Side Caching: Browser or mobile app caches responses locally.
  • Server-Side Caching: API server caches results in memory (e.g., in-memory cache, Redis).
  • Reverse Proxy Caching: Tools like NGINX, Varnish, or CDN cache responses at the edge.
  • Database Query Caching: Store results of expensive queries in cache for reuse.

3. HTTP Caching Headers

APIs often use HTTP headers to control caching:

  • Cache-Control: Defines caching policies (e.g., Cache-Control: public, max-age=3600).
  • ETag: Unique identifier for a resource version. Clients use it for conditional requests.
  • Last-Modified: Timestamp of last update. Clients can check freshness.
  • Expires: Specifies when a cached response becomes stale.

4. Example: ASP.NET Core Response Caching

// In Program.cs
builder.Services.AddResponseCaching();

var app = builder.Build();
app.UseResponseCaching();

app.MapGet("/products", async context =>
{
    context.Response.GetTypedHeaders().CacheControl =
        new Microsoft.Net.Http.Headers.CacheControlHeaderValue()
        {
            Public = true,
            MaxAge = TimeSpan.FromSeconds(60)
        };
    await context.Response.WriteAsync("Cached product list");
});

5. Example: Redis Caching in APIs

// Pseudocode for caching API response
var cacheKey = "products:all";
var cachedData = redis.Get(cacheKey);

if (cachedData != null)
{
    return cachedData; // Serve from cache
}
else
{
    var data = db.GetProducts();
    redis.Set(cacheKey, data, expiry: TimeSpan.FromMinutes(10));
    return data;
}

6. Best Practices

  • Cache only frequently accessed or expensive-to-compute data.
  • Set appropriate expiration times to avoid stale data.
  • Use ETag or Last-Modified for conditional requests.
  • Invalidate cache when data changes (cache busting).
  • Combine caching with CDN for global scalability.

Designing for Scalability in AKS (Azure Kubernetes Service)

1. Why Scalability Matters

2. Key Strategies

  • Cluster Autoscaler: Adjusts the number of nodes in the cluster when pods cannot be scheduled due to resource constraints.
  • Vertical Pod Autoscaler (VPA): Dynamically adjusts resource requests/limits (CPU, memory) for pods.

  • Stateless Design: Build services to be stateless so they can scale horizontally without dependency on local state.
  • Observability: Monitor metrics with Prometheus, Grafana, and Azure Monitor to trigger scaling decisions.

Partitioning Strategy in Azure Cosmos DB

1. Why Partitioning?

Partitioning allows Cosmos DB to scale horizontally by distributing data across multiple servers. It ensures high availability, predictable performance, and virtually unlimited storage capacity.

2. Key Concepts

  • Partition Key: A property in each item used to determine which partition it belongs to. Example: UserId, TenantId.
  • Logical Partition: All items with the same partition key value. Each logical partition can store up to 20 GB of data.
  • Physical Partition: The actual infrastructure unit managed by Cosmos DB. Logical partitions are mapped to physical partitions automatically.
  • Hierarchical Partition Keys (HPK): Multi-level partition keys (e.g., /tenantId/userId/id) that allow unlimited logical partition storage by spreading data across multiple levels.

3. Partitioning Strategy

  • High Cardinality: Choose a partition key with many unique values to distribute load evenly.
  • Balanced Workload: Avoid keys that cause uneven distribution (e.g., all data under one tenant).
  • Access Patterns: Select a key aligned with query patterns (e.g., if most queries filter by CustomerId, use it as partition key).
  • Hierarchical Keys: Use HPK when a single logical partition risks exceeding 20 GB.

4. Example

// Container with partition key = /UserId
Item1: { "UserId": "U001", "Name": "Alice" }
Item2: { "UserId": "U002", "Name": "Bob" }

// Logical partitions created:
Partition U001 → contains all items with UserId = U001
Partition U002 → contains all items with UserId = U002

5. Best Practices

  • Pick a partition key that evenly distributes data and request volume.
  • Use hierarchical partition keys for multi-tenant or high-volume scenarios.
  • Monitor partition metrics in Azure Portal to detect hot partitions.
  • Design queries to include the partition key for efficiency.

Implementing Retries in Azure Functions

Implementing retries in Azure Functions depends heavily on how your function is triggered and the level of control you need. There isn't a single "one size fits all" button because different triggers handle errors natively.

You can handle retries at four distinct levels:

1. Trigger-Level Built-in Retries (Best for Queues & Messages)

If you are using data-driven triggers like Azure Storage Queues or Azure Service Bus, you should usually avoid writing custom retry logic. These services have native retry and dead-lettering capabilities built into the host.

  • Azure Storage Queues: Configured in host.json. If a function fails, the message is automatically placed back in the queue. After maxDequeueCount attempts, it goes to a -poison queue.
  • Azure Service Bus: Handled on the Service Bus side via the Max Delivery Count setting. If a function throws an exception, the message locks expire and it tries again until it reaches the cap and hits the Dead Letter Queue (DLQ).

Example host.json for Storage Queues:

{
  "version": "2.0",
  "extensions": {
    "queues": {
      "maxDequeueCount": 5,
      "visibilityTimeout": "00:00:10"
    }
  }
}

2. Function-Level Retry Policies (Best for Timer, Event Hubs, Kafka)

For triggers that don’t have built-in message delivery states (like Timer or Event Hubs), the Azure Functions runtime provides native decorators/attributes.

⚠️ Note: The runtime evaluates these rules only if your function throws an uncaught exception. If you catch the exception and don't rethrow it, the runtime assumes everything went perfectly.

Strategy A: Fixed Delay

Retries a specific number of times, waiting a static amount of time between attempts.

[Function("ProcessTimerData")]
[FixedDelayRetry(5, "00:00:10")] // Retry 5 times, waiting 10 seconds between each
public async Task Run([TimerTrigger("0 */5 * * * *")] TimerInfo myTimer)
{
    // Your processing logic here. 
    // If it throws an unhandled exception, it will auto-retry.
}

Strategy B: Exponential Backoff

Increases the delay time between each attempt to give downstream services (like a database or an API) breathing room to recover.

[Function("SyncData")]
[ExponentialBackoffRetry(5, "00:00:02", "00:05:00")] 
// 5 retries. Starts at 2 seconds, scales exponentially, caps at 5 minutes.
public async Task Run([EventHubTrigger("messages", Connection = "EHConnection")] string[] events)
{
    // Your processing logic
}

3. Code-Level Resilience (Best for HTTP Triggers & Granular Control)

Function-level policies don't always apply well to HTTP Triggers (as you usually want to return a quick, managed error response to the client instead of hanging the HTTP request while the runtime retries).

For HTTP triggers or external API calls inside your functions, use code-level resilience libraries like Polly (.NET) or built-in wrapper logic in other languages.

// Example using Polly inside a C# Function
var retryPolicy = Policy
    .Handle<HttpRequestException>()
    .WaitAndRetryAsync(3, retryAttempt => TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)));

await retryPolicy.ExecuteAsync(async () => 
{
    return await _httpClient.GetAsync("https://api.external-service.com/data");
});

4. Durable Functions Orchestration Retries

If you are building long-running workflows using Durable Functions, you can specify a retry policy explicitly when invoking an Activity Function from an Orchestrator. This ensures your state survives across host restarts.

[Function("Orchestrator")]
public static async Task RunOrchestrator([OrchestrationTrigger] TaskOrchestrationContext context)
{
    var retryOptions = new TaskRetryOptions(
        firstRetryInterval: TimeSpan.FromSeconds(5),
        maxNumberOfAttempts: 3)
    {
        BackoffCoefficient = 2.0 // Exponentially doubles the wait time
    };

    // Calls the "CallExternalAPI" activity function using the retry policy
    await context.CallActivityAsync("CallExternalAPI", null, retryOptions);
}

Azure Storage Redundancy Options

1. Why Redundancy?

Azure Storage redundancy ensures that your data is durable, highly available, and resilient against hardware failures, network outages, or regional disasters. It replicates data across multiple locations depending on the chosen redundancy option.

2. Redundancy Types

Option Description Use Case
LRS (Locally Redundant Storage) Replicates data 3 times within a single datacenter in one region. Cost-effective, suitable for non-critical workloads where regional redundancy is not required.
ZRS (Zone-Redundant Storage) Replicates data synchronously across 3 availability zones in a region. High availability within a region, protects against datacenter failures.
GRS (Geo-Redundant Storage) Replicates data asynchronously to a secondary region (hundreds of miles away), plus 3 copies in the primary region. Disaster recovery, ensures durability even if the primary region is lost.
RA-GRS (Read-Access Geo-Redundant Storage) Same as GRS, but allows read access to the secondary region. Critical workloads needing read availability during regional outages.
GZRS (Geo-Zone-Redundant Storage) Combines ZRS in the primary region with asynchronous replication to a secondary region. Maximum durability and availability, recommended for enterprise-grade mission-critical apps.
RA-GZRS (Read-Access Geo-Zone-Redundant Storage) Same as GZRS, but allows read access to the secondary region. Best option for disaster recovery with read availability during outages.

3. Best Practices

  • Choose LRS for dev/test or non-critical workloads.
  • Use ZRS for high availability within a region.
  • Adopt GRS/RA-GRS for disaster recovery across regions.
  • Prefer GZRS/RA-GZRS for mission-critical enterprise applications needing both zone and geo redundancy.
  • Monitor replication health and configure alerts for failover scenarios.

4. Interview Insight

Managed Identity vs Service Principal in Azure

1. Overview

  • Managed Identity: An automatically managed identity in Azure Active Directory (AAD) assigned to Azure resources. It eliminates the need to manage credentials manually.
  • Service Principal: An application identity in AAD created explicitly to allow apps/services to authenticate and access Azure resources. Requires manual credential management (client ID/secret or certificate).

2. Key Differences

Aspect Managed Identity Service Principal
Creation Created and managed automatically by Azure when enabled on a resource Manually created in Azure AD by admins or developers
Credential Management No credentials to manage; Azure rotates automatically Requires storing and rotating secrets/certificates
Scope Tied to a specific Azure resource (VM, App Service, Function, etc.) Can be used by any application/service across environments
Security More secure (no secrets in code/config) Risk of secret leakage if not managed properly
Use Case Best for Azure-hosted workloads needing access to Azure resources Best for external apps/services or automation scripts needing Azure access

3. Example Usage


// Using Managed Identity in .NET
var credential = new DefaultAzureCredential();
var client = new SecretClient(new Uri("https://myvault.vault.azure.net/"), credential);

// Using Service Principal in .NET
var credential = new ClientSecretCredential(
    tenantId: "xxxx-xxxx-xxxx",
    clientId: "yyyy-yyyy-yyyy",
    clientSecret: "zzzzzzzz");

var client = new SecretClient(new Uri("https://myvault.vault.azure.net/"), credential);

4. Best Practices

  • Prefer Managed Identities for Azure-hosted workloads to avoid secret management.
  • Use Service Principals when external apps or automation scripts need Azure access.
  • Apply least privilege RBAC to both identities.
  • Rotate secrets regularly if using Service Principals.
  • Audit usage with Azure AD logs and Defender for Cloud.

  • Definition: Maintain two identical environments — Blue (current production) and Green (new version).

    • Deploy new version to Green environment.

    • Zero downtime deployment.
    • Easy rollback (switch traffic back to Blue).
    • Predictable cutover.
  • Limitations: Requires duplicate infrastructure, higher cost.

  • Definition: Gradually roll out new version to a small subset of users before full rollout.
  • Process:
    • Deploy new version to a small percentage of servers/users.
    • Monitor performance, errors, and user feedback.
    • Gradually increase rollout until 100% adoption.
  • Advantages:
    • Reduces risk by exposing issues early.
    • Allows real-world testing with minimal impact.
    • Supports progressive delivery strategies.
  • Limitations: More complex monitoring and traffic routing required.

Risk Management Rollback is instant Issues detected early with small impact
Infrastructure Cost High (duplicate environments) Lower (incremental rollout)
Complexity Simpler traffic switch Requires advanced routing & monitoring

  • Use Blue-Green for applications needing predictable cutover and instant rollback.
  • Use Canary for large-scale apps where gradual rollout reduces risk.

Implementing Rollback in CI/CD Pipelines

1. Why Rollback?

Rollback ensures service continuity when a deployment introduces failures. It allows reverting to a last known good version quickly, minimizing downtime and protecting data integrity.

2. Rollback Strategies

  • Blue-Green Deployment: Maintain two environments (Blue = current, Green = new). If Green fails, switch traffic back to Blue instantly.
  • Canary Release: Deploy to a small subset of users. If issues arise, rollback affects only the canary group before wider rollout.
  • Deployment Slots: In Azure App Service or Kubernetes, use slots/namespaces. Swap back to the previous slot if the new one fails.
  • Immutable Artifacts: Store versioned container images/packages. Rollback redeploys the last stable artifact.
  • Database Rollback: Use backward-compatible migrations, feature flags, or point-in-time restore for schema/data safety.

3. Example: Azure DevOps Pipeline Rollback

  steps:
  - script: kubectl apply -f deployment.yaml
    displayName: 'Deploy New Version'

  - script: |
      if ! kubectl rollout status deployment/myapp; then
        echo "Deployment failed, rolling back..."
        kubectl rollout undo deployment/myapp
      fi
    displayName: 'Rollback on Failure'

  • Monitor deployments with Application Insights, Prometheus, Grafana to trigger rollback automatically.

SonarQube Metrics Explained

1. Overview

SonarQube provides a set of quality metrics that measure different aspects of code health. These metrics are used to evaluate security, reliability, maintainability, test coverage, complexity, and duplications. They form the basis for Quality Gates, which enforce coding standards in CI/CD pipelines.

2. Key Categories of Metrics

🔐 Security

  • Security Rating: Grades from A (no issues) to E (critical issues).
  • Vulnerabilities: Number of security flaws detected.
  • Security Hotspots: Sensitive code areas requiring manual review.

⚙️ Reliability

  • Reliability Rating: Based on the number and severity of bugs.
  • Bugs: Issues that could cause incorrect program behavior.

🛠️ Maintainability

  • Maintainability Rating: Based on code smells.
  • Code Smells: Poor coding practices that make code harder to maintain.
  • Technical Debt: Estimated time to fix maintainability issues.

📊 Coverage

  • Coverage %: Percentage of code covered by unit tests.
  • Uncovered Lines: Lines of code not tested.

🔄 Duplications

  • Duplicated Lines: Percentage of code duplication.
  • Duplicated Blocks: Repeated code segments across files.

📈 Complexity

  • Cognitive Complexity: Measures how difficult code is to understand.
  • Cyclomatic Complexity: Number of independent paths through the code.

3. Why These Metrics Matter

SonarQube metrics help teams:

  • Detect issues early in the development cycle.
  • Prevent technical debt from accumulating.
  • Ensure secure, reliable, and maintainable codebases.
  • Enforce coding standards via Quality Gates in CI/CD pipelines.

Conditions:
- Coverage >= 80%
- Duplications < 3%
- Security Rating = A
- Reliability Rating = A
- Maintainability Rating = A

Optimizing Slow SQL Queries

1. Why Queries Become Slow?

SQL queries often slow down due to poor indexing, inefficient joins, large result sets, suboptimal query design, or missing statistics. Optimizing them ensures faster response times, better scalability, and reduced resource usage.

2. Key Optimization Strategies

📑 Indexing

  • Create indexes on frequently queried columns (WHERE, JOIN, ORDER BY).
  • Use covering indexes to avoid extra lookups.
  • Avoid over-indexing (too many indexes slow down writes).

🔄 Query Design

  • Use SELECT only required columns (avoid SELECT *).
  • Rewrite queries to reduce nested subqueries.
  • Prefer JOINs over correlated subqueries.

📊 Execution Plan Analysis

  • Use EXPLAIN or SET STATISTICS IO ON to analyze query plans.
  • Identify table scans and replace them with indexed lookups.
  • Check for missing or unused indexes.

⚙️ Database Tuning

  • Update statistics regularly for accurate query plans.
  • Partition large tables for faster access.
  • Use caching for frequently accessed results.

📉 Reduce Data Volume

  • Apply filters early in queries.
  • Use pagination for large result sets.
  • Archive old data to reduce table size.

3. Example Optimization


-- Slow query
SELECT * FROM Orders WHERE YEAR(OrderDate) = 2026;

-- Optimized query (index-friendly)
SELECT * FROM Orders 
WHERE OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01';

4. Best Practices

  • Always review execution plans before deploying queries.
  • Combine query optimization with index tuning.
  • Monitor queries using SQL Profiler, Extended Events, or Query Store.
  • Test performance improvements in staging before production rollout.

Indexing Strategies in SQL Server

1. Why Indexing Matters?

Indexes in SQL Server improve query performance by reducing the amount of data scanned. They act like a lookup table, allowing the database engine to quickly locate rows without scanning the entire table.

2. Types of Indexes

  • Clustered Index: Sorts and stores rows in the table based on the index key. Each table can have only one clustered index.
  • Non-Clustered Index: Stores a separate structure with pointers to the actual data rows. Multiple non-clustered indexes can exist.
  • Covering Index: Includes all columns needed by a query, avoiding lookups.
  • Filtered Index: Applies to a subset of rows (e.g., active users only).
  • Columnstore Index: Stores data in a columnar format, optimized for analytics and large datasets.
  • Full-Text Index: Enables fast text searches across large text fields.

3. Indexing Strategies

📑 Clustered Index Strategy

  • Choose a column that is unique, stable, and sequential (e.g., primary key, identity column).
  • Avoid frequently updated columns to reduce fragmentation.

🔄 Non-Clustered Index Strategy

  • Create indexes on columns used in WHERE, JOIN, ORDER BY, GROUP BY.
  • Use INCLUDE clause to add non-key columns for covering queries.

📊 Filtered Index Strategy

  • Use for queries targeting a subset of data (e.g., active orders).
  • Reduces index size and improves performance.

📈 Columnstore Index Strategy

  • Best for data warehouses and analytical queries.
  • Provides high compression and fast aggregations.

4. Example Index Creation


-- Clustered Index
CREATE CLUSTERED INDEX IX_Orders_OrderID ON Orders(OrderID);

-- Non-Clustered Covering Index
CREATE NONCLUSTERED INDEX IX_Orders_CustomerID
ON Orders(CustomerID)
INCLUDE (OrderDate, TotalAmount);

-- Filtered Index
CREATE NONCLUSTERED INDEX IX_Orders_Active
ON Orders(Status)
WHERE Status = 'Active';

5. Best Practices

  • Analyze queries using Execution Plans to identify missing indexes.
  • Limit the number of indexes to avoid overhead on INSERT/UPDATE/DELETE.
  • Regularly rebuild or reorganize indexes to reduce fragmentation.
  • Use Query Store and DMVs to monitor index usage.

6. Interview Insight

👉 In interviews, emphasize that indexing strategies involve choosing the right type of index (clustered, non-clustered, filtered, columnstore) based on query patterns. Highlight the importance of covering indexes, execution plan analysis, and maintenance to balance performance with storage and write overhead.

Schema Design for Multi-Tenant Applications

1. What Is Multi-Tenancy?

Multi-tenancy means a single application serves multiple customers (tenants), while ensuring data isolation, scalability, and security. The schema design determines how tenant data is stored and accessed.

2. Schema Design Approaches

🏢 Separate Database per Tenant

  • Isolation: Each tenant has its own database.
  • Pros: Strong isolation, easy backup/restore per tenant.
  • Cons: Expensive at scale, harder to manage migrations.

📑 Shared Database, Separate Schemas

  • Isolation: Each tenant has its own schema in a shared database.
  • Pros: Balance between isolation and manageability.
  • Cons: Schema proliferation, more complex migrations.

📊 Shared Database, Shared Schema

  • Isolation: All tenants share tables; tenant_id column differentiates data.
  • Pros: Most scalable, easier to onboard new tenants.
  • Cons: Requires strict row-level security and indexing strategies.

3. Key Design Considerations

  • Tenant Identifier: Always include TenantId in shared schemas.
  • Row-Level Security: Enforce isolation via SQL Server RLS or application logic.
  • Indexing: Create composite indexes (e.g., (TenantId, CustomerId)) for performance.
  • Partitioning: Use table partitioning by tenant for large datasets.
  • Encryption: Encrypt sensitive tenant data for compliance.
  • Auditing: Track tenant-specific changes for debugging and compliance.

4. Example: Shared Schema Design


CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    TenantId INT NOT NULL,
    CustomerId INT NOT NULL,
    OrderDate DATETIME,
    Amount DECIMAL(10,2),
    CONSTRAINT FK_Tenant FOREIGN KEY (TenantId) REFERENCES Tenants(TenantId)
);

-- Composite index for tenant isolation
CREATE INDEX IX_Orders_Tenant_Customer
ON Orders (TenantId, CustomerId);

5. Best Practices

  • Choose schema strategy based on scale, isolation needs, and compliance.
  • Automate migrations with tools like EF Core Migrations or Flyway.
  • Monitor performance per tenant to avoid noisy neighbor problems.
  • Use sharding for very large multi-tenant systems.

6. Interview Insight

👉 In interviews, emphasize trade-offs: separate DB = strong isolation but costly, shared schema = scalable but requires strict security. Highlight techniques like row-level security, composite indexing, and partitioning to show practical experience in designing multi-tenant schemas.

Relational vs NoSQL Databases: Trade-offs

1. Relational Databases (RDBMS)

  • Data Model: Structured, tabular format with predefined schemas.
  • Consistency: Strong ACID (Atomicity, Consistency, Isolation, Durability) guarantees.
  • Scalability: Typically vertical scaling (adding more power to a single server).

Handling Deadlocks in SQL Server

1. What Is a Deadlock?

A deadlock occurs when two or more transactions block each other by holding locks on resources and waiting for the other to release them. SQL Server detects deadlocks automatically and resolves them by terminating one transaction (the deadlock victim).

2. Strategies to Handle Deadlocks

🔄 Application-Level Handling

  • Catch SqlException with error code 1205 (deadlock victim).
  • Implement retry logic with exponential backoff.
  • Ensure transactions are idempotent so retries don’t cause data corruption.

📑 Query & Transaction Design

  • Keep transactions short and simple to reduce lock duration.
  • Access resources in a consistent order across transactions.
  • Use UPDLOCK or ROWLOCK hints to control locking behavior.
  • Break large operations into smaller batches.

📊 Indexing & Schema Optimization

  • Create proper indexes to reduce lock contention.
  • Use covering indexes to avoid unnecessary lookups.
  • Normalize schema to minimize lock conflicts.

⚙️ Isolation Levels

  • Use READ COMMITTED SNAPSHOT to reduce blocking with row versioning.
  • Consider optimistic concurrency for high-read workloads.

3. Example: Retry Logic in C#


int retryCount = 3;
for (int i = 0; i < retryCount; i++)
{
    try
    {
        // Execute SQL command
        break; // success
    }
    catch (SqlException ex) when (ex.Number == 1205)
    {
        // Deadlock victim
        if (i == retryCount - 1) throw;
        Thread.Sleep(1000 * (i + 1)); // exponential backoff
    }
}

4. Best Practices

  • Monitor deadlocks using Extended Events or SQL Profiler.
  • Log deadlock graphs for root cause analysis.
  • Educate developers to design queries with consistent resource access patterns.
  • Combine application retries with database tuning for resilience.

1. What Is Partitioning?

Partitioning is the process of splitting a large table or index into smaller, manageable pieces (partitions), while still being treated as a single logical object. It improves query performance, manageability, and scalability.

2. Partitioning Strategies

  • Data is divided based on ranges of values (e.g., dates, IDs).
  • Example: Orders partitioned by year.

🔢 List Partitioning

  • Data is divided based on discrete values (e.g., region codes).
  • Example: Customers partitioned by country.

⚙️ Hash Partitioning

  • Data is distributed using a hash function.
  • Balances load across partitions but less predictable.

3. Steps to Implement Partitioning in SQL Server

Step 1: Create a Partition Function

Defines how rows are mapped to partitions based on a column. 


CREATE PARTITION FUNCTION pfOrdersByYear (INT)
AS RANGE LEFT FOR VALUES (2020, 2021, 2022, 2023);

Step 2: Create a Partition Scheme

Maps partitions to filegroups for physical storage. 


CREATE PARTITION SCHEME psOrdersByYear
AS PARTITION pfOrdersByYear
TO (FG2020, FG2021, FG2022, FG2023, FG2024);

Step 3: Create a Partitioned Table

Apply the partition scheme to the table. 


CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,
    OrderYear INT,
    Amount DECIMAL(10,2)
) ON psOrdersByYear(OrderYear);

4. Benefits of Partitioning

  • Improves query performance by scanning only relevant partitions.
  • Enables partition elimination during queries.
  • Simplifies data management (e.g., archiving old partitions).
  • Supports parallel query execution.

5. Best Practices

  • Choose partition keys with high cardinality (e.g., dates, IDs).
  • Align partitioning with query access patterns.
  • Use filegroups to distribute partitions across storage.
  • Regularly monitor partition usage and adjust boundaries.

Designing Stored Procedures for Performance

1. Why Stored Procedures?

Stored procedures encapsulate SQL logic inside the database, improving performance, security, and maintainability. Well-designed procedures reduce network round-trips, leverage execution plan caching, and enforce consistent business rules.

2. Performance-Oriented Design Strategies

📑 Efficient Query Design

  • Use SELECT only required columns (avoid SELECT *).
  • Apply filters early to reduce scanned rows.
  • Prefer JOINs over correlated subqueries.

🔄 Parameterization

  • Use parameters instead of dynamic SQL to enable plan reuse.
  • Beware of parameter sniffing; use OPTION (RECOMPILE) or local variables if needed.

📊 Index & Execution Plan Awareness

  • Design queries to leverage clustered/non-clustered indexes.
  • Analyze execution plans to detect table scans or missing indexes.
  • Use covering indexes for frequently accessed queries.

⚙️ Transaction Management

  • Keep transactions short to reduce lock contention.
  • Access resources in a consistent order to avoid deadlocks.
  • Use appropriate isolation levels (e.g., READ COMMITTED SNAPSHOT).

📉 Reduce Overhead

  • Avoid unnecessary cursors; use set-based operations.
  • Minimize temp table usage unless required for performance.
  • Return only necessary result sets.

3. Example Stored Procedure


CREATE PROCEDURE usp_GetActiveOrders
    @TenantId INT,
    @StartDate DATE,
    @EndDate DATE
AS
BEGIN
    SET NOCOUNT ON;

    SELECT OrderId, CustomerId, OrderDate, Amount
    FROM Orders WITH (NOLOCK)
    WHERE TenantId = @TenantId
      AND OrderDate BETWEEN @StartDate AND @EndDate
      AND Status = 'Active'
    ORDER BY OrderDate;
END;

4. Best Practices

  • Use SET NOCOUNT ON to reduce network traffic.
  • Implement error handling with TRY...CATCH.
  • Document parameters and expected behavior.
  • Regularly review Query Store and DMVs for performance insights.

Transaction Isolation Levels

1. What Are Isolation Levels?

Isolation levels in SQL Server define how concurrent transactions interact with each other. They balance data consistency with system performance by controlling visibility of changes made by other transactions.

2. Common Problems Isolation Levels Address

  • Dirty Reads: Reading uncommitted changes from another transaction.
  • Non-Repeatable Reads: Same query returns different results within a transaction.
  • Phantom Reads: New rows appear in repeated queries due to inserts by other transactions.

3. Isolation Levels in SQL Server

🔓 READ UNCOMMITTED

  • Allows dirty reads, non-repeatable reads, phantom reads.
  • Fastest but least consistent.
  • Equivalent to WITH (NOLOCK).

📖 READ COMMITTED (Default)

  • Prevents dirty reads.
  • Allows non-repeatable and phantom reads.
  • Best balance for OLTP workloads.

🔒 REPEATABLE READ

  • Prevents dirty and non-repeatable reads.
  • Allows phantom reads.
  • Locks rows until transaction completes.

📸 SNAPSHOT

  • Uses row versioning instead of locks.
  • Prevents dirty, non-repeatable, and phantom reads.
  • Requires ALLOW_SNAPSHOT_ISOLATION enabled.

🛡️ SERIALIZABLE

  • Most restrictive level.
  • Prevents dirty, non-repeatable, and phantom reads.
  • Locks entire ranges; transactions behave sequentially.

4. Trade-offs

  • Performance: Higher isolation increases locking and blocking.
  • Deadlocks: More restrictive levels raise risk.
  • Snapshot: Requires tempdb space for row versioning.

5. Practical Guidance

  • Use READ COMMITTED for most applications.
  • Use SNAPSHOT for reporting or analytics with high concurrency.
  • Use SERIALIZABLE only when strict correctness is mandatory.
  • Avoid READ UNCOMMITTED unless stale/dirty data is acceptable.
Implementing Optimistic Concurrency in EF Core

1. What Is Optimistic Concurrency?

Optimistic concurrency assumes that conflicts are rare. It allows multiple transactions to read and modify data simultaneously, but detects conflicts at save time using a concurrency token. If another transaction has changed the data, EF Core throws a DbUpdateConcurrencyException.

2. Configuring a Concurrency Token

You typically use a RowVersion or Timestamp column in SQL Server. 


public class Person
{
    public int PersonId { get; set; }
    public string FirstName { get; set; }

    [Timestamp] // Marks as concurrency token
    public byte[] Version { get; set; }
}

3. How EF Core Generates SQL

When updating, EF Core includes the concurrency token in the WHERE clause: 


UPDATE [People]
SET [FirstName] = @p0
WHERE [PersonId] = @p1 AND [Version] = @p2;

4. Handling Concurrency Conflicts

You catch DbUpdateConcurrencyException and decide how to resolve conflicts: 


try
{
    await context.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    foreach (var entry in ex.Entries)
    {
        var databaseValues = await entry.GetDatabaseValuesAsync();

        // Option 1: Store Wins (discard client changes)
        entry.OriginalValues.SetValues(databaseValues);

        // Option 2: Client Wins (overwrite database)
        // entry.OriginalValues.SetValues(entry.CurrentValues);

        // Option 3: Merge (custom logic)
    }
    await context.SaveChangesAsync();
}

5. Resolution Strategies

  • Client Wins: Overwrite database values with client changes.
  • Store Wins: Discard client changes and reload from database.
  • Merge: Apply custom logic to combine values.

6. Best Practices

  • Always use RowVersion/Timestamp for concurrency tokens.
  • Log conflicts for audit and compliance.
  • Handle exceptions gracefully—avoid blind retries.
  • Use optimistic concurrency for most scenarios; fall back to pessimistic locking only for critical workflows.

Designing Database Sharding

1. What Is Sharding?

Database sharding is the process of splitting a large dataset into smaller, independent pieces called shards. Each shard is a separate database instance that holds a portion of the data. Sharding improves scalability, performance, and availability.

2. Why Shard?

Sharding is used when a single database cannot handle the volume of data or traffic. It enables horizontal scaling, reduces query response times, and distributes load across multiple servers.

3. Sharding Strategies

🔑 Key-Based Sharding

Data is distributed based on a shard key (e.g., UserId, CustomerId). This ensures even distribution but requires careful key selection to avoid hotspots.

📍 Range-Based Sharding

Data is divided into ranges (e.g., dates, numeric IDs). Simple to implement but can cause uneven load if ranges are skewed.

🌍 Geo-Sharding

Data is partitioned by geographic region. Useful for multi-region deployments to reduce latency and comply with data residency laws.

⚡ Directory/Lookup Sharding

A lookup service maps keys to shards. Provides flexibility but adds an extra layer of complexity and potential bottlenecks.

4. Schema Design Considerations

Each shard should have the same schema. Include a shard key in tables, ensure indexes align with query patterns, and design for cross-shard queries using aggregation services or APIs.

5. Implementation Approaches

- Use application-level routing (middleware decides which shard to query).
- Use database proxies (e.g., Vitess, Citus) for transparent sharding.
- Implement shard map managers (Azure SQL Elastic Database tools) for shard discovery.

6. Challenges

- Cross-shard joins are expensive.
- Resharding (moving data between shards) is complex.
- Operational overhead increases with more shards.

7. Best Practices

- Choose a shard key with high cardinality to distribute load evenly.
- Monitor shard health and balance regularly.
- Automate resharding and failover processes.
- Use global identifiers for cross-shard consistency.

8. Interview Insight

In interviews, emphasize that sharding is about horizontal scalability and requires careful shard key selection to avoid hotspots. Highlight trade-offs between range-based vs key-based sharding, mention cross-shard query handling, and show awareness of resharding complexity. public async Task<List<Product>> GetProductsAsync()

}

Mocking vs Stubbing

1. What Are Test Doubles?

In unit testing, test doubles are substitutes for real dependencies. They help isolate the unit under test and control its environment. Two common types are mocks and stubs.

2. Stubbing

A stub provides predefined responses to method calls. It does not care about how the method is invoked, only about returning controlled data. Stubs are used when you want to simulate data or behavior without verifying interactions. 


// Stub example with Moq
var stubRepo = new Mock<IRepository>();
stubRepo.Setup(r => r.GetByIdAsync(1))
        .ReturnsAsync(new Product { Id = 1, Name = "Laptop" });

// Service uses stubbed repository
var service = new ProductService(stubRepo.Object);
var result = await service.GetProductNameAsync(1);

Assert.Equal("Laptop", result);

3. Mocking

A mock not only provides responses but also verifies interactions. Mocks are used when you want to ensure that a dependency was called with the correct parameters, the right number of times, or in a specific order. 


// Mock example with Moq
var mockRepo = new Mock<IRepository>();
mockRepo.Setup(r => r.GetByIdAsync(It.IsAny<int>()))
        .ReturnsAsync(new Product { Id = 1, Name = "Laptop" });

var service = new ProductService(mockRepo.Object);
await service.GetProductNameAsync(1);

// Verify interaction
mockRepo.Verify(r => r.GetByIdAsync(1), Times.Once);

4. Key Differences

- Stub: Provides canned responses, does not verify behavior.
- Mock: Provides responses and verifies that interactions occurred.
- Stub: Focuses on state (what data is returned).
- Mock: Focuses on behavior (how methods are called).

5. Best Practices

- Use stubs when you only care about returning controlled data.
- Use mocks when verifying interactions and side effects is important.
- Avoid over-mocking, as it can lead to brittle tests.
- Prefer fakes (in-memory implementations) for complex dependencies.

CAP Theorem and Its Relevance

1. What Is CAP Theorem?

The CAP theorem states that in a distributed system, you can only guarantee two out of three properties at the same time: Consistency, Availability, and Partition Tolerance.

2. The Three Properties

- Consistency (C): Every read receives the most recent write. All nodes see the same data.
- Availability (A): Every request receives a response, even if some nodes are down.
- Partition Tolerance (P): The system continues to operate despite network partitions or failures.

3. Trade-Offs

- CP (Consistency + Partition Tolerance): Prioritizes accuracy of data, may sacrifice availability during partitions.
- AP (Availability + Partition Tolerance): Prioritizes responsiveness, may return stale data.
- CA (Consistency + Availability): Only possible if there are no partitions, which is unrealistic in distributed systems.

4. Examples

- CP Systems: Traditional RDBMS, MongoDB (in certain configurations).
- AP Systems: Cassandra, DynamoDB, CouchDB.
- CA Systems: Rare in practice, as real-world networks always risk partitions.

5. Relevance in Modern Architectures

- NoSQL Databases: Often choose AP for availability and scalability.
- Financial Systems: Often choose CP to ensure strict consistency.
- Cloud-Native Applications: Must tolerate partitions, so they balance between AP and CP depending on business needs.
- Microservices: CAP guides whether services should fail fast (consistency focus) or degrade gracefully (availability focus).

6. Interview Insight

In interviews, emphasize that CAP theorem is about trade-offs in distributed systems. Highlight that partition tolerance is unavoidable, so the real choice is between consistency and availability. Mention practical examples like Cassandra (AP) vs MongoDB (CP), and explain how business requirements drive the choice. Handling Distributed Transactions

1. What Are Distributed Transactions?

Distributed transactions occur when a single logical transaction spans across multiple services, databases, or message queues. Ensuring atomicity, consistency, isolation, and durability (ACID) across distributed boundaries is challenging due to network failures, latency, and partial failures.

2. Approaches to Handle Distributed Transactions

🔄 Two-Phase Commit (2PC)

- Coordinator asks all participants to prepare (phase 1).
- If all agree, coordinator sends commit (phase 2).
- Guarantees atomicity but can block resources and reduce availability.

⚡ Saga Pattern

- Breaks a transaction into a series of local transactions.
- Each step has a compensating action to undo changes if later steps fail.
- Works well in microservices and event-driven architectures.

📨 Eventual Consistency

- Accepts that data may be temporarily inconsistent.
- Relies on asynchronous messaging and retries to converge to consistency.
- Common in AP systems under CAP theorem.

🛠️ Idempotency

- Ensure operations can be retried safely without side effects.
- Critical for distributed systems where retries are common.

3. Example: Saga Pattern in .NET


// Order Service publishes event
await _bus.Publish(new OrderCreatedEvent(orderId));

// Payment Service consumes event
public async Task Handle(OrderCreatedEvent evt)
{
    var success = await _paymentGateway.ChargeAsync(evt.OrderId);
    if (!success)
        await _bus.Publish(new PaymentFailedEvent(evt.OrderId));
}

// Compensation (cancel order if payment fails)
public async Task Handle(PaymentFailedEvent evt)
{
    await _orderRepository.CancelOrder(evt.OrderId);
}

4. Best Practices

- Prefer Saga pattern over 2PC in microservices.
- Use message queues (Kafka, RabbitMQ, Azure Service Bus) for orchestration.
- Implement idempotent operations to handle retries.
- Monitor transactions with distributed tracing (Jaeger, Zipkin).
- Align design with business requirements (strong consistency vs eventual consistency).

CQRS and Event Sourcing

1. CQRS (Command Query Responsibility Segregation)

CQRS is an architectural pattern that separates read and write operations into different models:

- Command side: Handles writes (create, update, delete).
- Query side: Handles reads (fetch, search, report).

This separation allows each side to be optimized independently—for example, using a relational database for commands and a NoSQL store for queries.

✅ Benefits

- Scalability: Read and write workloads scale separately.
- Flexibility: Different storage technologies for commands vs queries.
- Clearer design: Explicit separation of responsibilities.

2. Event Sourcing

Event Sourcing is a pattern where state is derived from a sequence of events rather than storing the current state directly.

- Every change is recorded as an immutable event (e.g., OrderPlaced, PaymentProcessed).
- The system rebuilds state by replaying events.
- Provides a complete audit trail and supports temporal queries (what was the state at time X?).

✅ Benefits

- Auditability: Full history of changes.
- Debugging: Replay events to reproduce issues.
- Flexibility: Rebuild state in new ways (e.g., projections).

3. CQRS + Event Sourcing Together

CQRS and Event Sourcing complement each other:

- Commands generate events.
- Events are stored in an event store.
- Query side builds projections from events for fast reads.

4. Example in .NET


// Command
public record PlaceOrderCommand(Guid OrderId, string Product);

// Event
public record OrderPlacedEvent(Guid OrderId, string Product);

// Command Handler
public class PlaceOrderHandler
{
    private readonly IEventStore _eventStore;
    public PlaceOrderHandler(IEventStore eventStore) => _eventStore = eventStore;

    public async Task Handle(PlaceOrderCommand command)
    {
        var evt = new OrderPlacedEvent(command.OrderId, command.Product);
        await _eventStore.AppendAsync(evt);
    }
}

// Query Projection
public class OrderProjection
{
    private readonly List<OrderPlacedEvent> _events;
    public OrderProjection(IEnumerable<OrderPlacedEvent> events) => _events = events.ToList();

    public IEnumerable<string> GetProducts() => _events.Select(e => e.Product);
}

- Ensure events are immutable and versioned.
- Keep projections eventually consistent.
- Use idempotent handlers to handle retries safely.

Handling Eventual Consistency

1. What Is Eventual Consistency?

Eventual consistency is a consistency model used in distributed systems where updates to data are not immediately visible across all nodes, but the system guarantees that given enough time, all replicas will converge to the same state.

2. Why Use Eventual Consistency?

- Enables high availability under the CAP theorem.
- Improves performance and scalability by avoiding strict synchronization.
- Suitable for systems where temporary stale reads are acceptable (e.g., social feeds).

3. Techniques to Handle Eventual Consistency

🔄 Idempotency

Ensure operations can be retried safely without side effects. Critical for handling duplicate or delayed messages.

📨 Conflict Resolution

- Last Write Wins (LWW): Use timestamps to resolve conflicts.
- Custom Merge Logic: Apply domain-specific rules (e.g., sum counters).
- CRDTs (Conflict-Free Replicated Data Types): Mathematical structures that merge consistently across replicas.

⚡ Asynchronous Messaging

Use message queues (Kafka, RabbitMQ, Azure Service Bus) to propagate changes reliably and replay events if needed.

📊 Read Models / Projections

Maintain separate read models that are updated asynchronously from events. Clients accept that reads may be slightly stale.

🕒 Timeouts and Retries

Implement retry policies with exponential backoff to handle transient failures while ensuring eventual propagation.

// Producer publishes event
await _bus.Publish(new OrderCreatedEvent(orderId));

// Consumer updates read model asynchronously
public async Task Handle(OrderCreatedEvent evt)
{
    await _readModel.UpdateAsync(evt.OrderId, evt.Product);
    // Read model may lag behind, but will eventually catch up
}

- Use distributed tracing to monitor propagation delays.
- Apply compensating transactions for business-critical workflows.
- Choose AP systems

Designing a Logging Architecture

1. Purpose of Logging Architecture

A logging architecture provides a centralized, structured, and scalable way to capture, store, and analyze logs from distributed applications. It enables observability, debugging, auditing, and compliance.

2. Key Requirements

- Centralization: Collect logs from all services into a single system.
- Scalability: Handle high-volume logs from microservices and cloud workloads.
- Structure: Use structured formats (JSON) for easy parsing.
- Correlation: Include correlation IDs for tracing requests across services.
- Security: Mask sensitive data and enforce access controls.

3. Core Components

- Log Shippers/Agents: Collect logs (Fluentd, Filebeat, Logstash).
- Message Broker: Buffer and stream logs (Kafka, Azure Event Hub).
- Storage: Index and store logs (Elasticsearch, Azure Monitor, AWS CloudWatch).
- Visualization: Dashboards for analysis (Kibana, Grafana).
- Alerting: Trigger alerts on anomalies (Prometheus Alertmanager, Azure Monitor Alerts).

4. Example Architecture Flow

1. Applications emit logs in structured JSON with correlation IDs.
2. Log agents (Fluent Bit, Filebeat) collect and forward logs.
3. Logs are streamed via Kafka/Event Hub for durability.
4. Elasticsearch or cloud-native storage indexes logs.
5. Kibana/Grafana provides visualization and search.
6. Alerts are configured for error rates, latency spikes, or security violations.

6. Best Practices

- Use structured logs (JSON) instead of plain text.
- Include correlation IDs for distributed tracing.
- Apply log levels (Info, Warn, Error, Debug) consistently.
- Implement log rotation and retention policies.
- Integrate with SIEM systems for security monitoring.
